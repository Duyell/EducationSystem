# 技能使用规范（Skill Governance）

> 目的：本仓库同时存在 **栈无关技能** 与 **带技术栈假设的技能**。后者若不加约束，会把另一套技术栈的规则投影到本项目上。
> 本文件是第一、二层处理方案的**成文落点**：约定「谁管什么」与「冲突时听谁的」。
>
> 适用范围：在本仓库中工作的所有 agent（含子 agent）。新增/更新技能后请回看本文件。

---

## 一、技能清单与本项目相关性

| 技能 | 来源 | 触发条件 | 对本项目的定位 |
|---|---|---|---|
| `vue-best-practices` | Vue 官方 `vuejs-ai` 仓库，v18.0.0，git SHA 可溯 | 「任何 Vue 工作」（**有条件内降级分支**） | **代码维度权威**（见第二节） |
| `design-taste-frontend` | `~\.agents\skills\`，散装单文件，无版本/来源追踪 | 「任何前端/UI 工作」（**无条件内降级分支**） | **参考性审美来源**，需裁剪后使用 |
| `fe-ui-ts-linter` | SkillHub `global/` | 请求前端 UI/TS 审核时 | 前端改动自查工具，与上两者无冲突（写 vs 审） |
| `luban-kaiwu` | SkillHub `global/` | 开工编排 / 收尾质检 | 领域正交（需求与验收） |
| `skill-evaluator` | SkillHub `global/` | 需评测某技能时 | 领域正交（元工具） |

**关键不对称**：`vue-best-practices` 在遇到非 Vue 项目时会主动分派到 Options API / JSX 专用技能（`SKILL.md` L24-26）；`design-taste-frontend` **没有任何降级分支**，它假定 React + Next.js + Tailwind 成立，然后直接下发规则。

## 二、第一层：职责切分（谁管什么）

### 2.1 代码维度 → `vue-best-practices` 独家权威

以下决策**只**听 `vue-best-practices`，`design-taste-frontend` 无权干预：

- 组件划分与拆分触发条件（其 L74-89 给了客观拆分标准，例如超过 1 个明确职责、3+ 独立 UI 区块、CRUD 特性至少拆成容器/表单/列表/页脚）
- 入口与路由视图保持为「组合面」（composition surface），特性实现下沉
- `props down / events up`、`v-model` 的使用边界、`provide/inject` 仅用于深层共享
- composable（`useXxx()`）的抽取时机与 API 形态
- 单文件组件节序（`<script>` → `<template>` → `<style>`）
- 响应式模型最小化：`ref`/`reactive` 存源状态，其余用 `computed` 派生
- 类型契约：`defineProps` / `defineEmits` / `InjectionKey`
- 可选内置组件（`Teleport`/`Suspense`/`KeepAlive`/`Transition`）的选用时机
- 性能优化只在功能正确之后进行（其第 4 节明确「post-functionality pass」）

### 2.2 视觉维度 → `design-taste-frontend` 仅在明确做视觉任务时参考

**可迁移并允许采用**（与栈无关，属于设计判断力）：

| 内容 | 出处 | 说明 |
|---|---|---|
| 硬件加速守则 | §5 | 只动 `transform`/`opacity`，不动 `top/left/width/height` |
| z-index 克制 | §5 | 不为非层级需要滥用 `z-50`/`z-10` |
| 交互状态完整性 | §3 Rule 5 | loading / empty / error / 触觉反馈四态必须齐全 |
| 表单与数据模式 | §3 Rule 6 | label 在输入框上方、错误文本在下方、统一 `gap-2` |
| 排版与色彩校准思路 | §3 Rule 1、Rule 2 | 「用字重与颜色而非巨大字号建立层级」「单一强调色、饱和度克制」 |
| 避免 AI 套路化 | §7 | 假数据不要 `99.99%`、文案不用「赋能/无缝/一键」类套话 |
| 移动端布局塌陷 | §6 MOBILE OVERRIDE | 窄屏强制单列，防止横向滚动 |

**明确排除**（栈假设错误或与本项目体系互斥）：

| 被排除的内容 | 出处 | 原因 |
|---|---|---|
| 「Framework: React or Next.js，默认 RSC」「`'use client'` 隔离」 | §2（L21、L23） | 本项目是 Vue 3 SFC，整个前提不成立 |
| 「Tailwind CSS 覆盖 90% 样式」「T4 CONFIG GUARD」 | §2（L25-27） | 本项目用 Element Plus + `<style scoped>` |
| 图标必须用 `@phosphor-icons/react` / `@radix-ui/react-icons` | §2（L34） | 本项目用 `@element-plus/icons-vue` |
| Framer Motion 全套（`useMotionValue`/`useTransform`/`AnimatePresence`/`staggerChildren`）、§9 的「每张卡片必须有无限循环动画」 | §4（L71-74）、§9 | 无 framer-motion 依赖；本项目是后台 CRUD，表格场景上加无限动画是负收益 |
| 「紫色/蓝色 AI 审美禁用」（THE LILA BAN） | §3 Rule 2（L48） | 与本项目既有主色 `#165DFF` 冲突 |
| 「禁 Inter 字体」「禁 serif 用于 Dashboard」 | §3 Rule 1、§7 | 栈无关但需服从既有视觉体系，不单方面推翻 |
| 「禁 3 列等宽卡片布局」 | §7（L116） | 与 Element Plus 页面构成方式冲突 |
| 「ANTI-EMOJI POLICY [CRITICAL]：emoji 一律禁用」 | §2（L28） | 与现有实现冲突：`AiChatService` 的 SSE 状态文案使用 `🔄`/`⏸`/`⚠️`。**若确要执行此政策，必须作为一次独立重构，同时改前后端所有用户可见文案，不得在局部任务中顺手执行。** |

> 说明：`DESIGN_VARIANCE: 8` / `MOTION_INTENSITY: 6` / `VISUAL_DENSITY: 4`（其 L9-11）是通用审美基线，可作参考，但**不得**据此向本项目引入新依赖或推翻既有 UI 框架。

## 三、第二层：硬仲裁规则

当两个技能对同一决策同时开口时，按以下顺序裁决：

1. **项目现状优先**：`frontend/edu-system-client/package.json` 与既有代码风格是事实来源。任何技能都不得据其自身假设引入新依赖或替换技术栈。
2. **代码问题听 `vue-best-practices`**：涉及组件结构、数据流、响应式、类型、composable 的取舍，以其为准。
3. **视觉问题**：`design-taste-frontend` 的建议降级为「可选审美建议」，**且不改变技术栈、不新增依赖**；与既有视觉体系冲突时，维持既有体系。
4. **两者不冲突时同时采纳**：代码结构按其规范、视觉细节按裁剪后的设计规则，二者是正交的。
5. **无法裁决时**：在回复中显式说明分歧点与我的取舍理由，交由用户决定；**不得静默选一边**。

### 3.1 加载纪律（最容易被忽视、也是实际风险所在）

- **纯后端任务**（Java / MyBatis / SQL / agent 循环）**不加载任何前端技能**。
- **纯逻辑、类型、数据流改动的 Vue 任务**：只加载 `vue-best-practices`，不加载 `design-taste-frontend`。
- **明确的视觉/美化/新界面任务**：才同时加载，并按第三节裁决。
- **审核类任务**：用 `fe-ui-ts-linter`，不重复加载前两者做同一件事。

> 为什么这条最重要：`design-taste-frontend` 的触发条件是「任何 UI 工作」，在本项目里做**每一次**前端改动它都会生效。**未被察觉的隐性触发**比显式冲突更危险。

### 3.2 本项目的栈事实（技能不得违反）

| 项 | 事实 |
|---|---|
| 框架 | Vue 3.5 + Vite 8 + TypeScript strict（`vue-tsc --build`） |
| 组件写法 | `<script setup lang="ts">` + Composition API |
| UI 库 | Element Plus 2.13 + `@element-plus/icons-vue` |
| 状态 | Pinia 3 |
| 样式 | `<style scoped>`；主色 `#165DFF` |
| 依赖管理 | **npm**（`package-lock.json` 为准，勿用 pnpm） |
| 测试 | Vitest 4 + Playwright 1.58 |

## 四、执行前检查清单

动手改前端之前，逐条确认：

- [ ] 这个任务真的需要加载 `design-taste-frontend` 吗？（纯逻辑改动 → 不需要）
- [ ] 我是否准备引入新依赖？先查 `package.json`，且不因某个技能的偏好而引入。
- [ ] 组件拆分是否符合 `vue-best-practices` 的客观拆分触发条件？
- [ ] 视觉改动是否与既有 `#165DFF` / Element Plus 体系一致？
- [ ] 若两个技能给出相反建议，我是否按第三节裁决，并向用户说明了理由？
- [ ] 我是否在局部任务里顺手执行了「emoji 禁令」这类跨前后端的大范围重构？（不应如此）

## 五、维护约定

- **不要直接编辑 `~\.dsh\skills\` 下第三方技能的 `SKILL.md`**：它们是 vendored 产物，带 `.skillhub/metadata.json` 与逐文件 sha256（例如 `vue-best-practices` 还有 `SYNC.md` 记录上游 git SHA），`skillhub upgrade` 会覆盖你的本地修改。
- 需要项目级约束时，**写进本文件**（项目内、可版本控制、不受技能升级影响）。
- 技能升级后若其规则发生变化，请回看第二节的「排除清单」是否仍然成立。
- 本文件与 `docs/AI模块架构文档.md`、`docs/Agent化升级计划.md` 同属项目文档，改动请同步记录到 `docs/开发记录.md`。

### 🔥 本轮踩到的三个"坑"，都记进了接续指南

1. **沙箱挡住浏览器验证的两处**：`npm run dev` 倒在 Vite 的
   `windowsSafeRealPathSync → exec('net use')`；Playwright 用**命名管道**做 CDP
   （`--remote-debugging-pipe`）→ `spawn EPERM`。两者都是沙箱边界（不是代码问题），
   一次性提权重跑同一条命令即可——但**必须先知道**，否则很容易误判成"前端跑不起来"。
2. **脚本自己登录会顶掉自己的 token**：界面登录会把 Redis 里 `token:<username>` 换成新值，
   之前用 API 拿的 token 立刻失效。症状极具迷惑性：接口返回 `code=401`、`data=null`，
   而脚本里 `res.data || []` 会把它悄悄变成"空列表"→ 断言全部看起来正常。
   修法：界面登录后用 `page.evaluate(() => sessionStorage.getItem('token'))` 取页面里那个 token。
3. **`page.waitForFunction(fn, arg, options)` 的 options 是第三个参数**：
   我把它放在第二个位置，于是超时仍是默认 30s，报 `Timeout 30000ms exceeded` 时看着像产品卡住。

另一个**测试自身的错误假设**：我一开始断言"后建的会话必须排在前面"，
但服务端按 `update_time desc, id desc` 排序，而 `update_time` 是**秒精度**——
同一秒建的两个会话谁在前由 id 决定（确定性，但不等于"后建的在前"）。
改成断言"**界面顺序 == 接口顺序**"（这才是契约），并在注释里写明秒精度这个前提。

> 还有一条脚本卫生教训：清理逻辑只删"登记在册"的会话，而脚本中途失败时，
> 兜底新建的那个还没登记 → 上一轮把会话留在了库里，下一轮 phase A 看到的就是 4 条而不是 2 条。
> 现在改成"启动快照 + 结束前删掉快照之外的（两人各自核对一遍）"，并且**把删除失败计入断言**——
> 之前它只写在详情字符串里，条件不看它，失败也是 PASS。

### 多轮记忆：为什么没用框架自带的 `MessageWindowChatMemory`

计划里原本写的是"ChatMemory Bean 由 `MybatisChatMemoryRepository` 提供，窗口交给框架的
`MessageWindowChatMemory`"。真去接的时候读了一遍它的字节码，发现语义对不上：

```
add(id, messages):
  existing = repository.findByConversationId(id)
  merged   = process(existing, messages)      // 合并 + 裁剪到 maxMessages
  repository.saveAll(id, merged)              // 保存【整个窗口】
```

即 `ChatMemoryRepository.saveAll` 的语义是"用这一份**替换**该会话的全部消息"——
对内存实现（`map.put`）成立，落到 MySQL 只有两条路，都不行：

| 做法 | 后果 |
|---|---|
| 按语义**替换**（先删后插） | `ai_message` 只剩最近 20 条，界面上往上翻，早先的消息**永久消失**（"可查可审计"失效） |
| 当成**追加**插入 | 每轮把整个窗口再写一遍，消息成倍膨胀（第 3 轮 6 条 → 12 条） |

于是改成第三条路：`ai_message` 是**只追加的完整对话记录**（界面历史与审计读它），
模型上下文 = 从这份记录里**取最近 N 条**（`listRecent` 一条 SQL 的 `limit`）。
写入只有一个入口、窗口规则只有一处实现，也不再有"丢历史/消息翻倍"的取舍。
代价是没沿用框架窗口类；但窗口裁剪本身就是"取最近 N 条"，
单测里用"11 轮（22 条）后模型窗口 20 条、库里 22 条"把这条不变量钉住了。

### 🔥 Bug ①：同名工具跨角色互相覆盖 —— 学生问"我选了什么课"，助手答"你没选任何课"

**怎么发现的**：M2 端到端脚本没断言课程内容，但我去查审计表时看到
`get_my_courses` 的 `result_json = []`，而该生明明选了 6 门课（`course_selection` 里 6 行）。
补一条"工具返回的数据对不对"的测试（`StudentCourseListToolTest`）后立刻复现。

**根因**：`ToolRegistry` 把工具定义放在**一个全局 Map**（按工具名索引），
而学生与教师**各有一个同名的 `get_my_courses`**（学生＝我选的课、教师＝我教的课），
后注册的角色把前者覆盖掉。于是：

- 学生角色的**白名单校验通过**（名字确实在学生名单里）；
- 执行的是**教师那份实现**，拿学号当教师工号查课 → 空列表；
- 模型拿到的描述也是教师版的（从提示词层面就开始误导）。

**为什么此前全绿**：工具面测试（`AgentToolSurfaceTest`）只验证"工具在不在、角色对不对"；
评测脚本只看"模型有没有选对工具"（`ROUTING`）与"回答里有没有原始 JSON"；
**没有一处看过工具真的返回了什么数据**。

**修法**：定义改为 `Map<role, Map<name, ToolDefinition>>`，`getTool(role, name)` 必须带角色
（`AiChatService` 同步改为按角色取定义）。跨角色同名现在只记一条 INFO（这是合法用法，但值得留痕）；
同一角色内重复注册仍然 WARN。
回归测试 `ToolRegistryTest#sameToolNameIsIsolatedPerRole` 同时验证实现与**描述**都按角色隔离。

### 🔥 Bug ②：逐字符流式时，落单的 `</tool_call>` 照样漏给用户

上一轮（十八）刚补过"落单标签"的清理，但那次的用例把整段文本**一次性**喂进护栏，
标签在缓冲里是完整的，所以 `stripStrayTags` 删得掉。真实流式是**一个片段一个片段**来的：
护栏只把"半个**开**标签"扣住，于是 `</`、`t`、`o`…… 被逐段当普通文本发出去，再也删不掉。

**怎么发现的**：本轮新增的断言"**落库的助手正文**里不得出现工具调用残渣"
（`OutputGuardrailIntegrationTest`）——它把"发给用户"和"写进记忆"两份文本一起看了，
真机跑出来的落库正文是：

```
好的

</tool_call>你的平均学分绩点是 3.8834。
```

**修法**：`partialTagIndex` 同时匹配**开标签与闭标签**的前缀（两者只差一个 `/`），
把半截闭标签也扣在缓冲里；补一条**逐字符**喂闭合标签的单测（含 `cleanText` 不得含残渣）。

### 🔥 两个环境坑（都已解决，必须写进接续指南）

**① 本地明明有 Spring AI，Maven 离线模式却拒绝使用**

```
org.springframework.ai:spring-ai-bom:pom:1.0.9 (present, but unavailable):
Cannot access central in offline mode and the artifact has not been downloaded from it before
```

根因：本机 m2 里这批制品是**阿里云镜像**下载的，`_remote.repositories` 记录的来源 id 是
`aliyun-maven`；Maven 在 `-o` 模式会校验"制品来源 id 是否在当前构建的仓库列表里"，
而构建里的仓库是 `central` → **id 不匹配 → 本地有也不给用**。
修法：父 pom 里显式声明同 id 的仓库（`aliyun-maven`，就是这台机器 settings.xml 用的镜像），
让离线构建能认领本地制品。**没有**动 Maven 全局配置，也没有改本地仓库文件。

**② Spring AI 的传递依赖本地不全，必须联网拉一次；而沙箱不许写 `~/.m2`**

`spring-retry`、`spring-webflux`、`micrometer-core` 等不在本地仓库，联网拉取时 Maven 需要写
`C:\Users\...\.m2\repository\...\_remote.repositories`，被沙箱拒绝（`FileNotFoundException: 拒绝访问`）。
按规则**一次性提权**跑了同一条构建命令，把传递依赖补齐；之后 `mvn -o` 构建正常。
> 纪律：这类"就差一个文件写入权"的阻塞，提权一次即可，不要为了绕过它去改全局配置或手工拷 jar。

### 护栏补漏：落单的协议标签

基线评测**当场抓到**一个真问题（这正是"先跑基线再迁移"的价值）：

```
[FAIL] answer body shows no raw tool-call JSON -> imonial
</tool_call>您的当前平均学分绩点是 3.8834…
```

模型这次没吐完整块，而是吐了一个**没有配对的闭合标签**加几个字符残渣。
原护栏只处理"有开有闭的完整块"与"裸 JSON"，落单标签就这么漏给了用户。
修法：保留原有恢复逻辑，另把**落单的 `<tool_call>` / `</tool_call>`** 从要发出去的文本里清掉
（`stripStrayTags`，收尾段同样处理）。补 2 条单测（落单闭标签、落单开标签）。

### 为什么挂在 Service，而不是在 controller 与 AI 工具里各记一次

## 2026-09-22（十五）— 输出护栏：模型把工具调用写成正文时，接住它

计划里的"B 线"（M2 的前置小课题）落地。**没有新增任何权限**，只是把"模型偶尔走错通道"这件事接住。

| # | 修改项 | 状态 |
|---|--------|------|
| 1 | 新增 `duyell.ai.guard.ToolCallTextGuard`（流式识别 + 扣留 + 恢复调用） | ✅ |
| 2 | 接进 `AiChatService` 的工具循环：token 先过护栏；流结束时按"恢复出的调用"继续走正常流程 | ✅ |
| 3 | `ToolCallTextGuardTest` **9 项**（含**实测抓包原文**逐字符喂入）+ 接线层集成测试 **1 项** | ✅ |
| 4 | 评测新增**链路不变量**：回答正文不允许出现工具调用 JSON | ✅ |
| 5 | 真实模型回归：`--only=get_my_gpa,check_time_conflict` 2/2 通过（确认护栏没吞掉正常回答） | ✅ |

### 问题（P5 评测实测抓到，见开发记录 (十) 末节）

小模型偶尔**不走工具调用通道**，而是把调用**当成回答文本**吐出来：

```
bral
{"name": "approve_course_apply", "arguments": {"applyId": 1}}
</tool_call>
```

两个后果，第二个更糟：① 用户屏幕上出现一段原始 JSON；② **操作根本没发生**——
后端没收到工具调用，用户却以为提交了。7B 模型在本项目历史上 12 次实跑里出现 1 次，
属于**偶发**，靠"多跑几次"验证不可靠。

### 做法：识别 → 扣留 → 改道（而不是"过滤掉就算了"）

1. **扣留**：token 逐个先进 `ToolCallTextGuard`，它只把**确认安全**的文本发出去；
   怀疑是工具调用的部分（`<tool_call>` 标签、或 `{"name"...}` 这种裸 JSON）先压住。
2. **恢复**：流结束时把压住的内容解析成 `{name, arguments}`；
3. **改道**：把恢复出的调用**当成一次真实工具调用**塞回循环 —— 后续完全走原路：
   角色白名单 → 参数 Schema 校验 → 危险操作**确认卡片** → 审计。
   因此护栏**不是**安全边界的替代品，也**不会**让模型多出任何能力：
   提示注入让它复述一段 JSON，能做的事与它主动调用**完全一样**。

### 三个刻意的取舍

- **宁可漏认，不可吞字**：解析不出来就当普通文本原样发出。测试里专门有一条
  `malformedOrUnrelatedJsonIsShownAsText`（含 `{"title": "x"}` 这种无辜 JSON）。
- **不为识别牺牲体验**：缓冲上限 8000 字符，超了直接放行——不能为了"可能是个工具调用"把回答卡住。
- **原始 JSON 不写回模型历史**：恢复时助手消息的 content 置空（与正常工具调用一致），
  否则模型看到自己上次的原始 JSON，容易**反复复述**、陷入循环。

### 🔥 护栏自己也被测试抓到一个漏洞

第一条单测把**实测抓包原文按字符喂入**（真实流式一定会有这种切分），结果**没能恢复出调用**。
原因：识别"JSON 起点"时，我要求 `{` 后面已经跟了 `"name"` 的**非空前缀**，
于是**恰好停在 `{` 上的增量**被当成普通文本放走了（`{"name"` 就再也接不上）。
修法：把"空前缀"也算作可能起点（`"name".startsWith("") == true`）。
> 这条用例值得保留：**逐字符喂入**是最苛刻的切分方式，能逼出所有"提前放行"的边界错误。

### 验证结果

- `mvn -o -B test -pl edu-api -am`：**174 项**全绿（+10）
  - `ToolCallTextGuardTest` 9 项：恢复（含实测原文）、标签形式、跨增量不泄漏、半个标签、
    正常文本原样通过、非法 JSON 当文本、arguments 为字符串、多个调用、超大缓冲放行
  - `OutputGuardrailIntegrationTest` 1 项：用**继承 `OpenAiClient` 的桩**必现"坏模型"，
    断言 ① 恢复出的调用在**审计表里是 SUCCESS**（证明真的执行了、过了白名单与参数校验）
    ② 调用后**回到模型继续**（两轮）③ 原始 JSON 没写回历史
    （本项目测试类路径没有 Mockito，所以用子类覆盖 `streamChat`，不引入新依赖）
- 真实模型：`node .dsh/eval-p5-tools.cjs --only=get_my_gpa,check_time_conflict` → **PASS=45 FAIL=0**，
  ROUTING 2/2，其中包含新断言"回答正文不出现工具调用 JSON"

### 夹具卫生：中断的脚本会让 Java 测试红

UI 脚本第一次被中断（DSH 宿主崩溃会带走后台任务），残留了两行成绩夹具；
`AcademicWarningServiceTest` 再用同一 (课程, 学生) 插入就撞唯一键 `uk_score_course_student`，

### 关键设计：为什么是"水位线"而不是"未读标记"

需求是"只弹一次、可标记已读"，最容易写成"插一条未读记录、学生点掉改已读"。**没有那样做**，理由：

1. **读接口不产生写副作用**：若 `GET` 时插入未读记录，两个标签页同时打开就会插入两条，
   而且"查一次数据"变成"改一次数据"，很难解释。
2. 表 `academic_warning` 只记**学生确认过的水位线**（当时的未通过学分、门数、阈值快照）：
   - 当前值 **>** 水位线 → 才提示（首次触发时为"无水位线"，必然提示）；
   - 标记已读 = 把当前值记为水位线（唯一键 `student_id + failed_credits` 保证**幂等**）；
   - **情况变严重**（又挂科导致学分上升）→ 自然超过水位线 → 再提示一次。
3. 阈值快照存下来，便于回溯"当时是按什么标准预警的"（阈值以后可配置、会变）。

### 口径细节（都写进了文档与测试）

- 「是否通过」**委托** `GpaServiceImpl.isPassed`（补考通过记 60 的规则只有那一处实现），不重复实现；
- 同一课程代码多条成绩（重修）：**只要有一条通过就不算未通过**；学分取该代码各条记录的**最大值**
  （避免重修学分不同时少算）；
- 恰好**等于**阈值即触发（"达到阈值"）；
- 未达条件时"确认"**不写**水位线（否则会把"未预警"也记成水位线，掩盖以后的首次预警）。

### 三个踩到的坑（都不是业务逻辑问题，值得记）

1. **加了接口却忘了重新 `package`，拿着旧 jar 测了半天**：`mvn test` 只编译不重打包，
   运行中的仍是旧 jar，于是所有请求都落到"没有这个静态资源"（日志里是
   `NoResourceFoundException: No static resource academic-warning/my`）。
   **症状很像"权限规则写错"**（教师没被 403、学生 500），实际一眼就能分辨：
   日志里出现 `NoResourceFindException`＝**路由不存在**，即 jar 与源码不一致。
   → 纪律：**加/改接口后必须 `mvn -o -B package -DskipTests` 再起后端**（本仓库"重建前先停后端"的同类坑）。
2. **断言写在了错误的层面**：本项目对未知路径返回的是 **HTTP 200 + `{"code":"500"}`**，

3. **`.ps1` 又是非 ASCII**：新脚本第一版用中文注释，检查出 1127 个非 ASCII 字节。
   已整份改为英文注释（ASCII-only），并保留自动检查：
   `[System.IO.File]::ReadAllBytes(f)` 里 `>127` 的字节数必须为 **0**。

### 🔥 核对文档时揪出的两个真缺陷（都属于"同一规则被实现了两遍"）

**① AI 助手录入成绩绕过了 `ScoreService`**
`TeacherToolRegistrar` 的 `enter_score` / `update_score` 原本直接调 `scoreMapper`，自己算总分：
- **不写 `passed` 字段** → 落库为 NULL。而"是否已修过"的选课校验用的是
  `ScoreMapper.countPassedByCourseCode`（`and s.passed = 1`），
  于是**学生被录完成绩后还能重复选同一门课**（重复修读的漏洞）。
- **总分只保留 1 位小数**（`setScale(1)`），而 `ScoreServiceImpl` 是 3 位小数（与 `decimal(6,3)` 对齐）——
  **同一份成绩走助手与走界面得到不同总分**（87.65/91.35 得 89.9 vs 89.870），进而影响绩点。
> 修法：两个工具改为调用 `ScoreService.add/update`（总分权重、精度、`passed` 派生都只有那一处实现）。
> **教训**：项目里已经写明"规则只有一处实现"，但**新增工具时很容易绕过 Service 直接摸 Mapper**——
> 这次是靠"照着代码写文档"逐条核对才发现的，不是靠测试（原来的测试只测 Service 层）。

**② `evaluate_teacher` 的评分范围与界面不一致**
工具 Schema 写的是 `1~100`，而界面是 5 星控件（`el-rate :max="5"`），种子数据也是 5。
同一字段两套量纲，教师看到的平均分会被污染。→ 工具 Schema 改为 **1~5**，并在文档里统一为"5 星制"。

  1. **链路不变量**（必须全绿）：工具面与风险等级、确认卡片、危险操作在确认前**绝未执行**、
     取消后必须给出"已取消"、只读路径上工具**确实被执行**；
  2. **工具选择准确率**（是被测指标，按分数报告）：`ROUTING: n/10`，每条未命中都打印诊断分类
     （反问用户 / 把工具调用写成了文本 / 选错工具），低于阈值（默认 0.8）判整轮失败。
  > 把这两类混在一起，只有两种结局：要么被模型波动逼着放宽断言（等于放弃评测），
  > 要么为了全绿而假装模型的失误是代码 bug。分开之后，代码的契约仍然硬，模型的表现被如实计分。

### 🔥 评测抓到的三个真实缺陷（都是"看代码看不出来"的那种）

**① `LoginInterceptor` 在异步派发阶段重复鉴权 —— 会掐断正在流式输出的 AI 回答**
AI 对话的 SSE 流进行到一半时，如果同一用户在别处重新登录，Redis 里的 `token:<用户名>` 被新 token 覆盖；
SSE 完成时的 **ASYNC 派发**会让请求**第二次**经过拦截器，于是这个早已鉴权通过、响应已提交的请求被判
"登录已失效"；`reject()` 接着往已提交的响应里写 JSON，抛
`IllegalStateException: getOutputStream() has already been called`（表现为 500），
客户端看到的是 `TypeError: terminated`——**一次莫名其妙的断流**。
> 发现过程很值得记：这个 bug 是**我自己干扰出来的**——评测跑着的时候，我在另一个终端登录了同一个学生账号，
> 于是评测的第一条用例就 "stream error: terminated"。当时一度以为是评测脚本的锅，
> 直到去后端日志里看到 `LoginInterceptor.reject:179` 才明白。**并发登录不是异常场景，是日常场景**
> （手机 + 电脑、多标签页），所以这是真缺陷，不是测试环境问题。
修复：ASYNC 派发直接放行（第一次 REQUEST 阶段已经鉴权过，重查只有坏处）；
`reject()` 遇到已提交响应只记日志、不再写响应体。新增 `LoginInterceptorTest` **7 项**
（这个类是全部接口的唯一守卫，此前**一项测试都没有**）。

**② `recommend_courses` 反问用户 —— 描述写清了"省略会怎样"也没用**
学生问"我该选什么课？帮我推荐一下"，模型回了一句"您当前学期是哪个？"就结束了，**一个工具都没调**。
该工具的可选参数 `term` 在描述里已经写明"省略即覆盖所有已配置轮次的学期"——
也就是说，**坑不在描述里**，而在"模型倾向于先确认一句"。
修复：三个 system prompt 里各加一条硬规则——**不要为可选参数反问用户**，只有必填参数缺失时才提问。
> 这条经验的通用形式：**工具描述解决"模型不知道省略会怎样"，提示词解决"模型知道但想先问一句"。**
> 两者都要有，缺一个就会在某个模型上塌掉。

**③ `check_time_conflict` 只收 `courseId` —— 于是模型编了一个 id**
学生问"数据结构与算法这门课和我课表冲突吗"，模型选了正确的工具，但传了 `courseId=101`
（真实 id 是 3，库里只有 12 门课），工具返回"课程不存在"，**用户什么也没得到**。
根因不在模型：**用户永远只会说课程名，而工具只认 ID**，描述里那句"可用 get_course_list 查"
只是一句期望，模型完全可以跳过它。
修复：三种标识任选其一（`courseId` / `courseCode` / `courseName`），服务端解析；
同一代码/名称命中多个学期时**取最近学期并回显候选列表**（安静地比对另一个学期的课表，
结果看起来永远"合理"，用户不可能发现）。新增 `CheckTimeConflictResolutionTest` **8 项**，
含"编造的 id 必须给出可自救的错误"与"多学期必须列出候选"。
> 这是本轮最有价值的一条通用结论：**工具的参数形状要迁就用户实际会说的话，
> 而不是要求模型先做一次查询**。提示词叮嘱是软的，接口设计是硬的。

### ⚠️ 评测自己也错了两次，都是"绿得没有意义"

1. **判据根本读不到数据**：第一版评测用 `execFileSync` 调 mysql 客户端读审计表判断"模型选了哪个工具"，
   结果**每次都返回空**，于是每个用例都报"模型没有调用任何工具"，而审计表里明明躺着完全正确的记录。
   两个原因叠在一起：mysql 在 Windows 上打印"密码明文"警告后**退出码为 1**，
   而 `execFileSync` 对非零退出码**直接抛异常**（被我的 catch 吞掉）；
   更关键的是 **DSH 沙箱不允许子进程使用管道**（`spawnSync ... EPERM`），
   所以即便换成 `spawnSync` 也拿不到输出。
   → 最终**改成从 SSE 流里读工具名**（顺带促成了上面第 4 项改进）。
   > 教训：**一个不会失败的校验脚本比没有校验更糟**——它会持续给出"通过"的假象。
   > 校验脚本必须有"我能证明自己在看数据吗"的自检（现在脚本第一件事就是打印工具面规模）。

2. **断言断言了设计没承诺的东西**：取消危险操作后，后端**故意**不再向模型要一句话
   （半截的工具调用链回灌会被模型服务拒绝），收尾是一条"本次操作已取消"的状态文案。
   我最初的断言要求"必须有自然语言回答"，于是两条用例**假失败**。
   → 改成断言"必须给出明确的取消提示"。**断言要写设计真正承诺的行为，而不是我以为它该有的行为。**

3. **审计核对的时间窗把无关数据算了进来**：`AiAuditServiceTest` 会往**真实** `ai_tool_audit` 表写行
   （随机 `audit-<uuid>` 用户，其中还有 DANGEROUS `select_course` 的 SUCCESS 行），
   于是"本轮没有危险操作成功"这条断言被**单元测试的夹具**弄红——**为错误的理由失败**。
   → 改成 **id 水位线**：`-Mark` 在评测前记下 `max(id)`，评测后只核对 `id > 水位线` 的行，
   并增加"调用者只能是三个 golden set 账号"这条前置断言。
   > 运行顺序随之固定为：`mvn test` → `-Mark` → 评测 → 核对。**顺序反了就不是同一个结论。**

4. **最有用的一条断言：SUCCESS 不等于成功**
   上面第 ③ 个缺陷（编造 courseId）在评测里**是绿的**——工具确实被选中、也确实执行了、审计状态也是 SUCCESS，
   只有把 `result_json` 读出来才看见里面是 `{"error":"课程不存在…"}`。
   所以现在多了一条：**任何 SUCCESS 行都不允许带 error 载荷**。这条断言第一次跑就是红的，
   紧接着就是第 ③ 个修复。**"状态码绿"和"用户拿到了东西"是两件事。**

### ⚠️ 半开区间：与 P2 节次冲突**刻意不同**，不要再"统一"

| | 时间粒度 | 判据 | 端点相接 |

| 考试（P4） | 连续**时钟区间** | **半开区间** `a.start < b.end AND a.end > b.start` | **不算**冲突（11:00 结束 vs 11:00 开始） |

用户原则一致；`POST /exam/check` 供前端排考前试算。

### 🔥 本轮最大的坑：Windows PowerShell 5.1 会按 GBK 读无 BOM 的 .ps1，**把下一行代码吃掉**

现象：`verify-p4-api.ps1` 里所有带请求体的 POST/PUT 全部返回 500
（`StrictHttpFirewall: The request was rejected because the parameter name "{...json...}" is not allowed`），
而我在另一个 pwsh 里手写**一模一样**的调用却成功。排查了很久，最后在 `Api` 函数里打印
`$p.Keys` 才看到真相：**`ContentType` 这个键根本不在**——虽然它的赋值语句就在 `Body` 上一行。

根因：**本项目的命令实际由 Windows PowerShell 5.1 执行**（`$PSVersionTable.PSVersion` = 5.1，
不是 pwsh 7）。**PS 5.1 在没有 BOM 时按 ANSI/GBK 解码 .ps1**。我那次用 edit 工具往
`Api` 里加了几行**中文注释**，文件是无 BOM UTF-8；GBK 逐字节解码时，一个多字节汉字
跨过了行尾，于是**下一行（`$p['ContentType'] = ...`）被并进注释**里。
结果：Body 有值、ContentType 没有 → PowerShell 默认按 `application/x-www-form-urlencoded` 发送
→ Tomcat 把整个 JSON 当成一个**参数名** → Spring Security 防火墙拒绝 → 500。

**这是既有坑（"含中文的 .ps1 一律 ASCII-only"）的一个更隐蔽的变种**：
以前的表现是"解析直接报错"，这次是**静默少执行一行**——更危险，因为脚本照样能跑完。

修复与加固：
1. 所有校验脚本**重新审计并清空非 ASCII 字节**（现在 6 个 .ps1 全部 `non-ASCII=0`）。
   p4 里必须保留的中文**测试数据**（座位号段 `C区01-40`、监考人姓名）改成
   `[char]` 码点拼接（`('C' + $CN_AREA + '01-40')`），这样既能验证"中文往返不丢"，
   文件又保持 ASCII。
2. 在接续指南的"踩过的坑"里把 PS 5.1 + 无 BOM + 中文 的组合写成硬规则，
   并给出自查命令（统计 >127 的字节数，必须为 0）。

顺带发现并修掉的第二个编码问题：**请求体里的中文会被 PowerShell 换成 `?`**。
`-Body <字符串>` 不带 `charset=utf-8` 时，PS 按默认代码页发送（实测 `"D区01-20"` 到服务端变成 `"D??1-20"`）。
修复：`ContentType = 'application/json; charset=utf-8'`（已实测可正确往返；
**不要**改成传 `byte[]`——实测那种写法会让整批请求 400）。
前面几个脚本没暴露它，只因为它们**恰好没有在请求体里发中文**；现已全部统一加固。

### 顺带发现：未知路径返回 500 而不是 404（已知问题，未修）

### 一条排查纪律：先确认"路径前缀与环境"，再断言"服务挂了"
子代理报告"后端对**所有**已认证请求返回 500"，证据看似充分（连 P1/P2/P3 的接口也 500）。
实际原因是它**直连 8080 却带了 `/api` 前缀**——`/api` 只存在于前端 Vite 代理层，

### 用户明确的两条规则，落到代码里是这样

> 只有管理员**开启选课**后学生才能选；否则**只能看**
> 选课持续期间**可以退**，否则要等**补退选**期间才能退

所以"能不能选"是三个条件的合取：`status=1`（管理员开了开关）
∧ 学生在轮次适用范围内 ∧ 当前时间落在选课窗口内。少判任何一个都会放行不该放行的选课。
"能不能退"则是 `status=1` ∧（在选课窗口内 **或** 在补退选窗口内）。

**三个状态都做了种子数据**，时间窗用 `NOW()` 相对计算（写死日期的话过一阵子演示数据就全过期，
新装库的人会看到"所有轮次都已结束"，以为功能坏了）：

| 种子轮次 | 学期 | 状态 | 意图 |
|---|---|---|---|
| 第一轮选课 | 2024-2025-1 | status=1，选课窗口内 | 可选可退 |
| 补退选 | 2024-2025-2 | status=1，选课窗口已过、退课窗口内 | **只能退** |
| 第一轮选课（未开启） | 2025-2026-1 | status=0，窗口有效 | 只能看 |

### 六道校验链（只有一处实现）

```
1 轮次开启 → 2 适用范围 → 3 学分上限 → 4 未修过(同 course_code) → 5 无时间冲突 → 6 容量未满
```

- **校验方法返回"原因"而不是抛异常**（`selectionBlocker`）：这样"可选课程列表"能把原因

### 本轮发现的问题

1. **`SelectionStatus.readOnly()` 是又一个"派生方法不序列化"的坑**
   我在 record 上写了 `readOnly()` 想给前端用，但 **Jackson 只序列化 record 组件**，
   接口报文里根本没有这个字段——正是 P1 `AuditResult.satisfied()` 那个坑的翻版，
   而且这次是**我在已经踩过一次之后又踩了一次**。
   好在接口校验脚本第一时间把它照出来了（断言的 `$r.data.readOnly -eq $true` 直接失败）。
   已删除该派生方法，并在方法注释里写明"需要只读请在调用方用 `!canSelect && !canDrop` 推导"，
   测试里也加了一个 `readOnly(status)` 私有 helper 来承担这件事。
2. **把这条规则的边界搞清楚了（这次实测过，不是推测）**：
   | 形态 | 会不会进 JSON |
   |---|---|
   | **record** 的派生方法（如 `satisfied()`、`readOnly()`） | **不会**（Jackson 只认 record 组件） |
   | **POJO** 的 `isXxx()` / `getXxx()`（如 `SelectionRoundScope.isUnrestricted()`） | **会**（当属性 `unrestricted` 序列化） |
   | 任何带参数的方法（如 `matches(...)`） | 不会 |
   > 已用真实报文验证：`GET /selection-round/3/scope` 返回里确实有 `"unrestricted":false`。
   > 所以**"派生方法不序列化"只对 record 成立**，POJO 上的 `isXxx()` 是正常序列化的。
   > 我一度照搬了子代理"都不是序列化"的说法，实测后纠正——**这类结论必须自己验一遍**。
3. **冲突提示只给了课程名，没给课程代码**
   同一门课可能有多个教学班、名称也可能重复，改成 `《课程名》(课程代码)`，
   学生才能定位到具体哪一门（接口断言专门校验了代码出现）。
4. **种子数据根本测不到第 4/5/6 道校验**
   - 全库**不存在**"已通过但没选过"的课程（第 4 道无从触发）
   - 种子里三门有课表的课分别排在周一/周二/周三，**两两不重叠**（第 5 道无从触发）
   - 全库**没有满员课程**（第 6 道无从触发）
   所以第 4/5/6 道放在接口校验脚本里，用可清理的 fixture 覆盖（造一个"同一课程代码的另一个教学班"
   触发第 4 道、给两门课排重叠的课表触发第 5 道、造一门容量 1 的课并让另一学生选满触发第 6 道）。
   单元测试只覆盖**不写库就能验证**的部分，类注释里写明了这个分工。
5. **又是"Promise reject 未接住"这一类缺陷（这次在前端）**
   `ElMessageBox.confirm` 在用户**取消**时是 **reject**，不是返回 false；
   4 处（开关轮次、删除轮次、删除范围、退课）都会因此抛未处理的 Promise 异常，
   已全部 `try/catch`。这和 P1 的 `formRef.validate()` 是**同一个缺陷类别**，已在下方单列。

### 冲突判据（全项目只此一处）

用户确认的规则：**同一学期 且 星期几相同 且 节次区间重叠 且 周次区间重叠**。
区间重叠用**闭区间**判据 `a.start <= b.end AND a.end >= b.start`：

| 情形 | 结果 |
|---|---|
| 第 1-2 节 vs 第 3-4 节 | **不冲突**（相接不算） |
| 第 3-4 节 vs 第 4-5 节 | **冲突**（第 4 节重叠） |
| 第 1-16 周 vs 第 17-18 周 | 不冲突 |
| 第 1-16 周 vs 第 9-16 周 | 冲突（CS105 就是第 9 周开始的课） |

判据写在 SQL 里（`ClassTimeMapper.xml#selectConflicts`），教室推荐的空闲判定
（`RoomMapper.xml#pickFreeRooms` 的 `not exists`）必须与它**逐字一致**——
写成 `<` 就会变成"相接也算冲突"；两处不一致就会出现"检测说不冲突、推荐却说教室被占"。

**因为判据在 SQL 里，它的测试只能是集成测试**：把 Mapper stub 掉的单测只能验证 Java 分支，
验证不了重叠判据，而重叠判据恰好是这块唯一容易写错的地方。故 `ScheduleServiceTest`
直接打真库、**只读**、不做任何写操作，可重复执行。

### 两个审批流（刻意分开）

用户需求：教师申请开课 → 管理员审批 → 生效；且"教师排课"是单独一步。
故 `course_apply`（开课）与 `class_time_apply`（排课）**各自一张表、各自一条审批流**：

```
教师提交开课申请 → 管理员审批通过 → 生成 course 行（course_code 沿用申请里的）
                → 教师对已通过的课程提交排课申请 → 管理员审批
                → 审批环节硬校验冲突：有冲突则不落 class_time，
                  把冲突详情写进 conflict_info 并报错
```

管理员**没有**"直接插一条课表"的接口，这是刻意的：所有排课都必须留痕在
`class_time_apply` 里（谁申请、谁审批、有没有冲突），否则课表不可追溯。

### 本轮发现并修复的 4 个真实缺陷

1. **提交排课申请时的冲突提示根本没落库**
   `ClassTimeApplyMapper.add` 的 INSERT 少了 `conflict_info` 列，服务里
   `apply.setConflictInfo(...)` 写了个寂寞——提交时明明检出了冲突，教师回头再看申请记录却是空白。
   修复：INSERT 带上 `conflict_info`。（"审批被冲突挡住"那条是通过的，所以只有提交环节的
   提示丢了，属于容易漏掉的那一半。）
2. **自动分配的教室没有回写到申请行**
   审批时若没指定教室，服务会推荐一间并写进 `class_time`，但 `class_time_apply.room_id`
   仍是 NULL。结果：课表说"教1-101"，申请记录说"未分配"——审计链断了。
   修复：`updateReview` 增加 `roomId`（用 `COALESCE` 写，驳回时不抹掉教师期望的教室）。
3. **P1 遗留：`course.course_code` 从未接到 POJO/Mapper**
   P1 建了这一列并用它做培养计划/已修判定的地基，但 `Course` POJO 没有 `courseCode` 字段、
   `CourseMapper.add` 不写它、`CourseMapper.xml` 的 update 也不更新它 →
   **管理员在页面上新建的课程，course_code 永远是 NULL**，判断类功能会静默失配
   （不报错，只是永远匹配不上）。P2 的"审批通过生成 course"正好依赖它，故一并修复，
   并加了 `selectIdByCode` 供排课/选课反查。已在接口层验证（新建课程能带回课程代码）。
4. **`edujwxt.sql` 里放课表种子会写入 NULL 主键**
   `edujwxt.sql` 只建了 CS101/CS102 两门课，其余 10 门在 `seed_data.sql` 里；
   课表种子按 `course_code` 反查 `course.id`，放在 `edujwxt.sql` 里查不到 CS105 →
   `Column 'course_id' cannot be null`，**新装库直接失败**。
   修复：课表种子移到 `seed_data.sql`（那里 12 门课才齐），并用 `EXISTS` 保护。

### 新装的坑（PowerShell，一天内踩了三个）

1. **函数返回数组会被 PowerShell 展开，`.Count` 随之失效**
   `function Arr($v) { return @($v) }` 在只有 1 个元素时返回的是那个元素本身，
   而 **`PSCustomObject` 上的 `.Count` 返回的是"空"（不是 0，也不是 1）**，
   于是断言里拼出 `rows=`，看着像数据是空的，其实数据在。
   修复：计数一律用 `function Cnt($v) { ... return @($v).Count }`（返回真正的 Int32），
   管道/筛选/取下标则用**内联** `@($x)`（内联表达式不经过函数返回，不会被展开）。
   > 这个坑很危险：它让"数据是空的"和"断言写错了"长得一模一样。
2. **逗号比 `+` 结合更紧**
   `@('GET', '/room/free?term=' + $TERM + '&x=1')` 会被解析成 3 个元素
   （`'GET'`、`'/room/free?term='`、`$TERM + '&x=1'`）。必须给拼接加括号。
3. **用正则批量改脚本时括号配平被破坏**
   把 `(Arr $x) |` 替换成 `(@($x) |` 时多出一个左括号，整段脚本直接解析失败。
   教训：批量改完要**立刻跑一遍**，别指望"看起来对"。

## 2026-09-20（二）— 修复「有哪些课程可以选？」不调用工具、反而追问的问题（完成）

| 3 | 端到端验证脚本区分只读/危险操作，消除误报 | ✅ |

### 现象（用户实测发现）

用户问「有哪些课程可以选？」，AI 回答：
> 请提供想要搜索的课程名称…如果您不提供具体的课程名称，我将返回所有可选课程的信息。

即**模型反问用户**，而不是直接查询并列出课程。

### 排查过程（先证事实，再下结论）

1. **查审计表**：没有该次对话的记录 → 说明模型**根本没调用工具**，不是调用了出错。
2. **查后端日志**：无 `/ai/chat` 相关 SQL → 确认没有工具执行。
3. **复刻请求直接问 Ollama**：这一次却调用了工具 —— 但**凭空编造了参数** `courseName="leon"`（毫无来源）。
4. **跑 9 用例探针**：8/9 正确，只有「有哪些课程可以选？」这种问法失败。

结论：**不是稳定的功能缺陷，而是 7B 模型对「可选参数」处理不稳**，同一提问有三种行为：
反问用户 / 传空值 / 编造参数。而旧描述只说了"支持按名称搜索"，
**从未说明"不传会返回什么"**，给了模型猜测的空间。

### 修复

把「参数省略时的行为」明确写进工具描述与参数描述，覆盖全部 **6 个**带可选筛选参数的工具：
`get_course_list`、`list_users`、`list_students`、`list_teachers`、`list_courses`
（以及参数描述由"（可选，用于搜索）"改为"省略则返回全部"）。

`get_course_list` 的新描述还显式提示了触发说法：
> 查看可选课程列表。不传 courseName 时返回全部可选课程；用户说"有哪些课能选""列出所有可选课程"时，直接调用本工具且不要追问课程名称。

| 描述版本 | 调用率 | 干净地请求全部 |

| 旧（改之前） | **3/5** | 3/5 |
| 新（改之后） | **5/5** | 5/5 |

新描述下 5 次全部返回干净的空参数 `{}`。

### 二、由此暴露的缺陷：审计状态值被静默截断

真实模型提交越界评分（9999）触发参数校验路径后，日志出现：
```
审计字段超长已截断: column=status, maxLen=16, actualLen=17
```
**根因**：`status` 列为 `varchar(16)`，而 `INVALID_ARGUMENTS` 与 `DUPLICATE_SKIPPED` 都是 **17 字符**，
被写成 `INVALID_ARGUMENT` / `DUPLICATE_SKIPPE`。后果是**按 status 聚合时记录被分到错误分组**，
且"幂等命中"标记失真——审计数据在悄无声息地变错。

**为何 39 项单测没拦住**：测试只用了短状态值（SUCCESS/FAILED 等），
没有任何测试把常量长度与真实表结构做核对。这是"测试全绿但缺陷存在"的典型。

**修复过程本身也踩了一个坑，值得记录**：第一次只把数据库列扩到 `varchar(32)`，
**漏改了应用层的 `MAX_STATUS_LEN = 16`**，于是仍被应用层截断；
而当时新写的守护测试**只查了数据库列宽**，因此照样通过，直到再跑一次真实 LLM 才暴露。

### 详细说明

**① 表设计要点**
- 状态取值：`SUCCESS` / `FAILED` / `DENIED`（越权或未知工具）/ `REJECTED_BY_USER`（用户取消或确认超时）
- `confirm_id`：人工确认过的写操作可回溯到具体的那一次确认
- `request_id` + 唯一约束：现已建好，为阶段 0.6 的幂等保护预留（当前写 NULL，MySQL 唯一索引允许多个 NULL，不影响现有写入）
- 索引按 `user_id` / `tool_name` / `status` 分别配 `created_at`，支撑阶段 4 的聚合查询
- 迁移脚本用 `CREATE TABLE IF NOT EXISTS`，**可重复执行**（已实测重复执行 exit=0）
- `AiToolAuditMapper` 刻意只有 insert / 查询，**没有 update 与 delete**：审计是不可变事实

**② 设计取舍**
- **审计失败绝不外抛**：用户不该因为日志表写不进去而无法选课。但失败必须留 `ERROR` 级日志——「审计静默失效」比「没有审计」更危险。该不变量有专门测试覆盖。
- **越权调用的风险等级记 `UNKNOWN`**：不返回该工具真实的 `risk_level`。调用者本就无权使用它，泄露其存在性与等级属不必要的权限信息外泄。
- **定长列截断防御**：`user_id`/`role`/`tool_name`/`risk_level`/`status`/`confirm_id` 超出列宽时截断并告警，而不是让 MySQL 拒绝整条 INSERT。

**③ 修掉一个「写了但不可能生效」的实现**
`awaitConfirmation` 原返回 `String`，且内部在 `awaitDecision` 之后立即把 `awaitingConfirmId[0] = null`。
因此拒绝路径若去读 `awaitingConfirmId[0]` 记录审计，`confirm_id` **永远是空**。
改为返回 `ConfirmationOutcome(approved, confirmId, result)` 显式带出令牌——审计需要它，不能依赖已被清空的挂起状态。

**④ 测试过程中踩到的三个坑（都已修正，值得记录）**
1. **`Data too long for column 'user_id'`**：测试用 `"audit-test-" + 完整 UUID`（47 字符）超出 `varchar(32)`，INSERT 被 MySQL 拒绝。而「审计失败不外抛」的设计把它伪装成了「查不到数据」这一误导性症状——排查花了几轮。教训：吞异常的防御性设计必须配合足够醒目的告警，否则会掩盖真实故障。
2. **`@SpringBootTest` 默认回滚**：Spring Boot 给每个测试方法套一个回滚事务，审计写入在方法内即被回滚（计数不增、查询为空）。已实测确认后加 `@Transactional(propagation = NOT_SUPPORTED)` 关闭，审计测试才有意义。
3. **测试间数据污染**：审计表只追加、不回滚，共用同一 `user_id` 会让 `listByUser` 读到历史运行累积的记录（期望 1 条实际 3 条）。改为每个测试生成独立 `user_id`。
4. **「测试通过」不等于「测试稳定」**：修好上面三点后单次 18/18 全绿，但**第二次运行**时 `oversizedIdentifierIsTruncatedInsteadOfRejectingTheWholeRow` 失败（期望 1 条实际 2 条）——该用例输入是固定的 `"u".repeat(100)`，截断后每次都得到同一个 32 字符 `user_id`，按它查回必然累积。

   教训：只要测试会写真实持久化存储，就必须验证**连续两次运行的结果一致**，而不是只看一次绿。

`spring-boot-starter-test` 3.5.16 在离线仓库中解析到的 mockito/byte-buddy 组合在 JDK 21 上无法初始化 `MockMaker`。且 Spring Boot 测试支持会在**上下文启动时主动探测 Mockito**，导致全部 `@SpringBootTest` 用例失败（与是否真的用 mock 无关）。已在 `edu-api/pom.xml` 排除 `mockito-core` 与 `mockito-junit-jupiter`；需要桩时手写，本项目测试不依赖 Mockito。

**③ 一处自我更正：SSE 的 Content-Type 没有 charset，这不是缺陷**
我最初把「`text/event-stream` 未声明 `charset=utf-8`」判为真实缺陷，理由是实测同一响应用 UTF-8 与 Latin-1 解码结果不同（确实不同）。
**该判定是错的**：SSE 规范规定 `text/event-stream` 只有 UTF-8 一种有效编码、且无法声明其他编码，因此不带 charset 参数是**规范正确**行为，浏览器与遵循规范的客户端一律按 UTF-8 处理（本项目前端 `TextDecoder` 亦默认 UTF-8）。
曾尝试给 `SseEmitter` 传 `MediaType.TEXT_EVENT_STREAM`，经 `javap` 确认 Spring 6.2.8 的构造器只有 `()` 与 `(Long)`，该重载不存在，遂回退。脚本中改为输出 `[NOTE]` 而非断言。

**④ 环境踩坑（对后续开发有复用价值）**
- **Windows PowerShell 5.1 把 `.ps1` 按 ANSI 读取**：脚本内含中文会破坏语法解析（报"意外的标记"）。故验证脚本刻意写成纯 ASCII，对中文响应的断言改用 UTF-8 字节解码 + Unicode 码点拼接（`[char]0x5BC6`）。
- `Invoke-WebRequest` 在响应头无 charset 时按 Latin-1 解码 body，直接字符串匹配中文会得到乱码与假阴性 → 应读 `RawContentStream` 自行 UTF-8 解码。
- `mvn install` 在离线模式缺 `maven-install-plugin` 依赖 → 改用 `mvn package` 产出 fat jar，以 `java -jar` 启动，绕开 `install`
- `mvn spring-boot:run -pl edu-api -am` 会把 `run` 目标作用到父 pom（无主类）而失败 → 应先构建，再对目标模块运行
- 重建 fat jar 前必须先停止运行中的后端（Windows 文件锁导致 `repackage` 无法 rename）

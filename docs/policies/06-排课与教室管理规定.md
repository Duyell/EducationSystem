# 排课与教室管理规定

> 文档编号：**JW-06**　｜　适用范围：教学单位、任课教师、全体学生　｜　版本：**v1.1**（2026-09-20 审计修订）
> 图例：**⚙** = 系统已自动校验，数值与代码一致；**【制度】** = 管理制度条文，系统当前不自动校验。
> **v1.1 修订**（依据作者审计意见）：节次结构写清为上午 5 节 + 下午 5 节（同构）；
> 新增"排课按学期、每学期排一次"的说明；新增第 2A 节（按教学班排课，年级不参与排课）。
> 修订明细见文末。

---

## 1. 总则

1.1 排课是确定课程"在哪个学期的星期几、第几节、第几周、哪间教室上课"的过程。排课结果直接决定学生课表与冲突判定。**⚙**

1.2 排课实行**申请—审批**制：教师提交排课申请，教务处（管理员）审批通过后生效。**⚙**

1.3 **不允许上课时间冲突**：教师、教室、学生三个维度都不得撞课。**⚙**

## 2. 时间的表示方法

2.1 **学年与学期**：一个学年分为**两个学期**，学期编号采用 `YYYY-YYYY-N`
（例如 `2024-2025-1` 表示 2024-2025 学年的**第一学期**，`2024-2025-2` 为第二学期）。**⚙**

2.1.1 **排课以学期为单位，每学期排一次课**。**⚙**
- 源头上，"每学期排一次"是因为**开课本身是按学期的**：一门课在一个学期开一次，
  就有一条**独立的开课记录**（`course` 一行，带 `term`），上课时间挂在该次开课上
  （`class_time.course_id → course.term`）。
- 因此**同一门课在下一学期再开时，是另一条开课记录**（同一课程代码、不同 `course_id`），
  需要**重新排课**——教师重新申请开课、重新安排星期/节次/周次/教室。
- **为什么不"按年"排一次**：同一门课上下学期的教师、周次、节次、教室都可能不同；
  若按年存一份时间，就必须在一条记录里塞下两个学期的差异，反而更绕。
  而且**选课、考试本来就是按学期组织的**，排课按学期才与它们对齐。
- **系统里没有"学年"实体**：学年只体现在学期编号 `YYYY-YYYY-N` 里；
  所有业务（开课、排课、选课、考试、成绩）都以**学期**为粒度。

2.2 **星期**用 1~7 表示（1 = 周一，7 = 周日）。**⚙**

2.3 **节次**：一天排 **10 节**，用 1~10 表示；**上午 5 节（1~5）＋下午 5 节（6~10）**，
下午的结构与上午**同构**。**⚙**

| 时段 | 节次 | 常见排法（**【制度】**，系统不限定） |
|---|---|---|
| 上午 | 1、2 | 一次课通常为 2 课时 |
| 上午 | 3、4、5 | 可连排 3-5 节（3 课时），也可只排 3-4 节（2 课时） |
| 下午 | 6、7 | **结构与上午 1、2 相同**：一次课 2 课时 |
| 下午 | 8、9、10 | **结构与上午 3、4、5 相同**：可连排 8-10 节（3 课时），也可只排 8-9 节（2 课时） |

> **系统只认 1~10 的节次编号**，不校验"上午/下午"这个划分本身（它由作息时间表规定，
> 例如每节 45 分钟、课间 10 分钟）；但**节次编号与上表的结构是全校统一的**，
> 排课、课表展示与冲突判定都基于它。

2.4 系统用**节次区间**（起始节次 ~ 结束节次）记录上课时间，而不是固定"两节"或"三节"，因此支持上述各种排法。**⚙**

2.5 **周次**：支持**任意周次区间**，例如第 1-16 周、第 9-16 周（**非整学期开课是允许的**）。**⚙**
系统允许填写 1~53 周；学校实际校历一般为 **16 周教学周**（**【制度】**，由校历规定，系统不强制）。

2.6 **不做单双周**排课。**⚙** 如需隔周上课，应拆分为两条时间安排。

## 2A. 排课的对象：教学班，不是行政班

2A.1 **系统按"教学班"排课**：一条开课记录（`course` 一行）就是**一个教学班**，
排课排的是这个教学班的时间与教室。**⚙**

2A.2 **年级/专业/学院不参与排课本身**，它们只用于两件事：**定位培养方案**（专业 + 年级）
与**限定选课轮次适用范围**（年级/专业/学院）。**⚙**

2A.3 **冲突检测的三个维度**是**教师、教室、学生**（见第 4 节）——"学生"这一维度是
**逐人**判定的：某学生选了这门课，才会拿他的其他已选课程来比对。**⚙**
因此"4 个年级、上千名学生"并不会让排课变复杂：**每个教学班排一次**，
学生各自选课后按人校验冲突。

2A.4 **学生多怎么办**：同一门课学生多，就**开多个教学班**
（同一课程代码、多条开课记录，可以分不同教师/时间/教室），容量按教学班分别控制
（`course.max_student`）。**⚙**

2A.5 **按行政班整班上课的处理方式（经确认，2026-09-22）**：
本系统是**学分制选课**模型——学生**自己选课**，课表由"已选课程 + 已排时间"生成。**⚙**
- 需要"整班上课"的必修课，做法是**为这个班开一个教学班**（一条开课记录），学生各自选课；
- **系统不提供"按班级批量选课/整班导入名单"**。经作者确认（2026-09-22）**本阶段不做**该能力：
  它属于教务系统的"排课侧"功能，与本次升级（把系统做成有规则判断 + Agent 可操作）无关，
  且选课记录本身要求逐条可追溯（谁、何时选了哪门课）。
- 若将来确实需要，可在现有选课链路上加一个"管理员按班级批量选课"入口
  （仍须逐条经过六道校验：容量、冲突、已修过等），不影响现有数据模型。**【制度】＋有意的设计选择**

## 3. 教室资源

3.1 全校现有教室 **800 间**：**教1 ~ 教8** 共 8 栋，每栋 1~10 层，每层 10 间。**⚙**

3.2 教室编号规则为 **楼栋-楼层房间号**，例如 `教1-101`（教1 楼 1 层 01 室）、`教1-1001`（教1 楼 10 层 01 室）。**⚙**

3.3 教室类型与数量、容量：**⚙**

| 类型 | 数量 | 容量范围 |
|---|---|---|
| NORMAL（普通教室） | 648 间 | 60 ~ 220 人 |
| LAB（实验室） | 80 间 | 60 ~ 240 人 |
| MULTIMEDIA（多媒体教室） | 72 间 | 均为 240 人 |

3.4 每间教室有**启用/停用**状态，只有**启用**状态的教室可被安排上课。**⚙**

3.5 **【制度】** 教室由教务处统一调配；多媒体教室、实验室优先保障有相应教学需求的课程。

## 4. 冲突判定

4.1 **冲突判据**：以下四项**同时成立**才算冲突。**⚙**

```
冲突 ⟺ 同一学期 且 星期相同 且 节次区间重叠 且 周次区间重叠
```

4.2 区间重叠的判定公式为**闭区间**：`a.起始 ≤ b.结束 且 a.结束 ≥ b.起始`。**⚙**

4.3 ⚠️ **首尾相接算冲突**：第 **3-4 节**与第 **4-5 节**共用第 4 节，**判定为冲突**。**⚙**
> 原因：节次是"格子"，同一节课不能同时属于两个安排。

4.4 冲突从**三个维度**分别检查，任一维度冲突即拒绝：**⚙**
1. **教师**：同一教师在同一时段不能上两门课；
2. **教室**：同一教室在同一时段不能被两门课占用；
3. **学生**：学生已选课程与该课程时间不得重叠（选课时校验）。

4.5 该冲突判据在系统中**只有一处实现**，排课审批、选课校验、空闲教室查询共用同一套判定。**⚙**

## 5. 教室分配与推荐顺序

5.1 需要分配教室时，系统按以下规则推荐：**⚙**
1. 只取**已启用**且**容量 ≥ 需求人数**的教室；
2. 排除在该时段**已被占用**的教室；
3. 按「**容量 → 楼栋 → 楼层 → 房间号**」**升序**排序，取前若干间。

5.2 **排序刻意不用数据库自增编号**：教室是批量生成的，自增编号随安装批次变化，
按编号排序会让推荐结果在不同环境下不一致。按"容量 + 楼栋 + 楼层 + 房间号"排序，**任何环境下结果都相同**。**⚙**

5.3 推荐不到教室时，系统区分两种原因并明确说明：**"没有满足容量的教室"** 与 **"该时段教室都已占满"**。**⚙**

5.4 **【制度】** 教室容量应为上课人数的 1.0~1.2 倍；课程人数超过最大教室容量时，应拆班或调整教学安排。

## 6. 排课申请与审批

6.1 教师提交排课申请，内容包括：课程、星期、起始/结束节次、起始/结束周次、期望教室（**可以留空**）。**⚙**

6.2 **留空教室时，由系统按第 5 节的规则推荐并分配**，审批通过后写入正式上课安排。**⚙**

6.3 管理员审批时系统执行冲突校验；**存在冲突则拒绝**，并说明与哪门课、哪个教室、星期几、第几节、第几周冲突。**⚙**

6.4 审批通过后，该安排立即参与课表展示、选课时间冲突判定与空闲教室计算。**⚙**

6.5 **调课（变更上课时间或教室）同样走排课申请流程**，不得直接修改已生效的安排。**⚙**

6.6 一门课可以有**多条**上课时间安排（例如周一 1-2 节 + 周三 3-4 节）。**⚙**

## 7. 课表发布

7.1 学生课表按"已选课程 + 已生效的上课安排"生成；**尚未排课的课程会明确提示"尚未排课"**，不参与时间冲突判定。**⚙**

7.2 **【制度】** 课表在开学前一周发布。课表发布后如需调整，应提前通知学生。

## 8. 附则

8.1 本规定由教务处负责解释。

8.2 与系统行为不一致时，以系统实际行为为准，并及时修订本文件。

### 与系统实现的关系（供审计）

| 条款 | 系统是否自动校验 | 依据 |
|---|---|---|
| 2.1 / 2.1.1 **排课按学期、每学期排一次** | ⚙ 是（数据模型保证） | `course.term`（一次开课一行）；`class_time.course_id → course.id`，**`class_time` 上没有 term 字段**——学期只能来自开课记录，所以"一学期一份时间"是模型强制的 |
| 2.2 星期 1~7 | ⚙ 是 | `ClassTime.MIN_WEEKDAY/MAX_WEEKDAY`，`ScheduleServiceImpl.validateSlot` |
| 2.3–2.4 一天 10 节（上午 5 + 下午 5）、节次区间 | ⚙ 是（节次范围）；结构为**制度约定** | `ClassTime.MIN_PERIOD/MAX_PERIOD = 1/10`（报错文案"节次必须在 1~10 之间（一天 10 节）"）；系统不校验"上午/下午"划分本身 |
| 2A.1–2A.2 按教学班排课、年级不参与排课 | ⚙ 是 | 排课挂在 `course`（教学班）上；年级/专业/学院只用于 `training_plan` 定位与 `selection_round_scope` |
| 2A.3 冲突三维度中含"学生"（逐人判定） | ⚙ 是 | `ClassTimeMapper.selectStudentConflicts(studentId, courseId)` |
| 2A.4 多教学班（同代码多条开课） | ⚙ 是 | `course_code` **无唯一约束**，同一代码可有多条开课记录 |
| 2A.5 按行政班整班上课 / 批量选课 | **有意不做**（作者 2026-09-22 确认）；有替代做法 | 无批量选课接口，学生逐个选课（选课记录要求逐条可追溯）；需要"整班上课"时为其开一个教学班 |
| 2.5 周次区间任意、非整学期 | ⚙ 是 | `validateSlot` 只要求 `起始 ≥ 1` 且 `起始 ≤ 结束`；AI 工具 Schema 上限 53 |
| 3.1–3.4 800 间教室与类型/容量/状态 | ⚙ 是 | `room` 表（程序化生成：8 栋 × 10 层 × 10 间；NORMAL 648 / LAB 80 / MULTIMEDIA 72） |
| 4.1–4.5 冲突判据（闭区间、三维度） | ⚙ 是 | `ScheduleServiceImpl.checkConflict` + `ClassTimeMapper.selectConflicts` / `selectStudentConflicts` |
| 5.1–5.3 教室推荐顺序 | ⚙ 是 | `RoomMapper.pickFreeRooms`（`order by capacity, building, floor_no, room_no`） |
| 6.1–6.5 排课申请审批流 | ⚙ 是 | `ScheduleServiceImpl.applyClassTime` / `approveClassTimeApply`（冲突即拒绝、自动分配教室） |
| 7.1 未排课提示 | ⚙ 是 | `list_my_class_times` 工具输出 `unscheduledCount` 与"尚未排课"说明 |
| 2.6 不做单双周 | ⚙ 是 | `class_time` 无单双周字段（如需隔周须拆两条） |
| 3.5 / 7.2 教室调配与课表发布时限 | ❌ 未实现 | 无教务排班策略、无课表发布状态 |

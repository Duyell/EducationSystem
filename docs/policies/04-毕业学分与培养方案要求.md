# 毕业学分与培养方案要求

> 文档编号：**JW-04**　｜　适用范围：全日制本科生　｜　版本：v1.0（2026-09-20）
> 图例：**⚙** = 系统已自动校验，数值与代码一致；**【制度】** = 管理制度条文，系统当前不自动校验。
> ⚠️ 本文档中的**具体学分数值为演示用示例方案**（见第 5 节），真实教学计划以学校正式发布的培养方案为准。

---

## 1. 总则

1.1 培养方案是学生修读课程与毕业审核的依据。每个**专业 + 年级**对应一个培养方案版本。**⚙**

1.2 培养方案按"专业 + 年级"定位：学生所属专业由其班级（`clazz`）对应的专业确定，年级取班级的年级。**⚙**

1.3 培养方案中的课程分为**必修**与**选修**两类，并给出各课程的**学分**与**建议修读学期**。**⚙**

1.4 **课程代码（`course_code`）是培养计划与成绩、选课之间的唯一关联依据**：同一门课在不同学期开设时共用同一代码。
系统**不为课程代码设唯一约束**（同一代码可以有多条开课记录）。**⚙**

## 2. 毕业条件

学生须同时满足以下三项，方可毕业：**⚙**

| 序号 | 条件 | 判定方式 |
|---|---|---|
| 1 | **必修课全部通过** | 逐门比对培养方案中的必修课程，每门都必须有"已通过"记录 |
| 2 | **选修课学分达标** | 已通过的选修课学分总和 ≥ 培养方案规定的选修学分要求（修哪些不限） |
| 3 | **总学分达标** | 已修总学分 ≥ 培养方案规定的总学分要求 |

2.1 三项条件**缺一不可**。系统在审核时会输出：是否满足、已修学分、学分缺口、**未通过的必修课清单**、以及按分类的明细。**⚙**

2.2 审核结论可直接用于学业预警、毕业预审等场景；系统**不自动生成**预警或退学结论（见 JW-01 第 5 节）。

## 3. 学分认定规则

3.1 只有**已通过**的课程才计入已修学分（判定见 JW-03 第 2 节）。**⚙**

3.2 **学分取自实际修读课程的开课记录（`course.credit`），而不是培养计划中列出的学分。** **⚙**
> 这样处理的原因：同一门课在不同学期开课时学分若有调整，以学生**实际修读的那次**为准，
> 避免"计划里 3 学分、实际修了 4 学分却只认 3 学分"。

3.3 同一课程代码有多条成绩记录时，按课程代码归并，**学分只计一次**；绩点取最优记录（见 JW-03 4.4）。**⚙**

3.4 补考通过的课程按 60 分通过，学分正常计入。**⚙**

3.5 **【制度】** 转专业、转学、校外交流等取得学分的认定，须经教务处审批后录入；本系统**未实现**学分认定流程。

## 4. 培养方案的维护

4.1 培养方案由教务处（管理员）在系统中维护，包括方案名称、适用专业与年级、总学分、必修学分、选修学分要求，以及课程明细（课程代码、名称、类别、建议学期、学分）。**⚙**

4.2 培养方案的新增与修改通过管理端接口完成；**学生端只读**。**⚙**

4.3 **【制度】** 培养方案一经发布，原则上在一个培养周期内不做变更；因教学计划调整必须变更时，应提前一学期公布，并明确新老版本的适用对象。

4.4 **【制度】** 个别学生因转专业、留级等原因需要修读非本年级方案时，由教务处单独确认其适用方案。**系统未实现"个别学生换版"功能**（仅预留设计说明）。

## 5. 示例方案的数值（演示数据）

> ⚠️ 下表是本演示系统内置的**示例方案**，用于功能验证，**不是真实教学计划**。
>
> **2026-09-22 决定（作者授权我判断）**：**不编造真实教学计划**。理由：编一份"看起来像真的"的 4 年方案
> 只会让演示数据更像伪造；而且现有 12 门课/40 学分的方案足以驱动全部功能（毕业审核、推荐课程、
> 学业预警、绩点排名）——**机制的验证与课程门数无关**。
>
> **需要真实数据时怎么替换**（10 分钟的事）：把真实培养方案整理成
> `plan_course`（`plan_id, category, course_code, course_name, credit, suggest_semester`）与
> `training_plan`（总学分/必修/选修要求）两张表的插入语句，放进 `docs/sql/` 下的新迁移脚本，
> 再同步 `edujwxt.sql` / `seed_data.sql`；**同时更新本文第 5 节的数值与 `docs/开发记录.md` 里引用的数字**
> （毕业审核、推荐课程、学业预警的示例结果会随之变化）。

## 6. 附则

6.1 本要求由教务处负责解释。

6.2 培养方案的正式发布版本与本文件不一致时，以系统中维护的方案为准。

### 与系统实现的关系（供审计）

| 条款 | 系统是否自动校验 | 依据 |
|---|---|---|
| 1.1–1.3 按专业+年级定位方案 | ⚙ 是 | `training_plan(major_id, grade)` + `student_plan` 定位（`TrainingPlanServiceImpl`） |
| 1.4 课程代码为唯一关联依据 | ⚙ 是 | `course.course_code`（**无唯一约束**，这是有意设计） |
| 2 毕业三项条件 | ⚙ 是 | `CreditServiceImpl.auditGraduation` |
| 3.1/3.3/3.4 学分认定 | ⚙ 是 | `CreditServiceImpl`（`passedScoresByCode` + `creditOf`） |
| 3.2 学分取自实际开课记录 | ⚙ 是 | `CreditServiceImpl.creditOf` 取 `course.credit`（**不是** `plan_course.credit`） |
| 4.1–4.2 方案维护与学生端只读 | ⚙ 是 | `/training-plan` 仅管理员可写（`LoginInterceptor` 规则），`/training-plan/my` 学生只读 |
| 4.4 个别学生换版 | ❌ 未实现 | `student_plan_override` 仅预留设计，未建表 |
| 5 示例方案数值 | ⚙ 是（种子数据） | `training_plan` / `plan_course` 表当前内容 |

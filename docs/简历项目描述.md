> 用途：投递 Java 后端 / AI 应用（Agent）方向的简历项目条目。
> 写法取向：**以"做了什么功能、解决了什么问题、怎么证明有效"为主**，技术名词只在必要处出现，
> 保证每一句都能被追问、也答得上来。

## 版本 A（推荐：4 条主述 + 1 条架构底）

**项目名称：教务系统（个人项目 · Java 后端 + AI 助手）**

项目简介：把原本只能"增删改查"的教务系统，改造成一套**能做教学规则判断**、并且
**能用自然语言提问、动数据前先请用户确认**的教学管理系统。

- **业务规则落地**：实现培养计划与毕业学分审核（必修是否全部通过、选修学分还差多少）、
  绩点与专业内排名、智能排课与教室推荐（800 间教室、自动检测上课时间冲突）、
  选课开放与选课/退选（按轮次、范围、时间、重复、学分上限、名额六道校验）、考试安排与冲突检测，
  以及教师开课申请 → 管理员审批的完整流程。
- **AI 助手能真正回答问题**：学生可以直接问"我学分够毕业吗""我该选什么课""我下周有考试吗"，
  助手自行跨多张表取数后作答，给出具体数字与清单（已修/毕业所需学分、绩点与排名、还差哪些必修课、
  推荐哪些课、有没有时间冲突），而不是泛泛而谈；教师可让它查课程与学生名单、提交开课申请，
  管理员可让它审批开课。
- **安全边界与可追溯（重点）**：按角色隔离能力——学生只能看到自己的数据、教师没有绩点与选课功能、
  只有管理员能审批；涉及重要变更的操作（选课、录入/修改成绩、提交开课申请、申请排课、审批开课）
  都会先弹出确认卡片，**用户确认之前数据库不会有任何变化**；助手每次查数/改数都留痕
  （谁、何时、调用了哪个功能、参数与结果、成功还是失败），出问题可回溯；
  还有频次限制，防止对话被反复刷。
- **质量保障**：自建一套自动化验证——包含让**本地真实大模型**跑 10 个典型问题，
  逐条核对"有没有选对功能、答案里的数字与数据库是否一致"（当前 10/10 通过），
  以及业务规则、权限、前后端页面的分层检查；全项目自动化检查共 **881 项**。
  过程中据此修掉若干真实缺陷（例如助手需要课程编号、但用户只会说课程名，
  于是改成可直接按课程名/课程代码查询）。

- **架构（一句带过）**：Maven 多模块分层（对外接口 / 业务实现 / 公共能力），
  Spring MVC + MyBatis 数据访问与统一参数校验；JWT 登录认证 + 角色权限拦截；
  Redis 存登录态与高频查询并设 TTL 与主动失效。

## 版本 B（压缩版：3 条，篇幅紧张时用）

**项目名称：教务系统（个人项目 · Java 后端 + AI 助手）**

- **把"记录型"系统升级为"会判断"的系统**：落地培养计划与毕业学分审核、绩点与专业内排名、
  智能排课与教室推荐（800 间教室、时间冲突检测）、选课轮次与六道校验的选课/退选、
  考试安排与冲突检测、开课申请审批流。
- **做出可用的 AI 助手**：支持按角色用自然语言查数与办理业务（学生查学分/绩点/考试/课表、
  要选课推荐；教师查学生名单、申请开课；管理员审批），答案给出可核对的具体数字；
  按角色隔离可用的功能，重要变更先弹确认卡片、确认前不改任何数据，全部操作留痕可回溯；
  有频次限制。自建自动化验证（含真实大模型跑 10 个典型问题的选路与答案核对），全项目 881 项检查。
- **架构与安全**：Maven 多模块分层，Spring MVC + MyBatis + 统一参数校验；
  JWT + 角色权限拦截；Redis 缓存登录态与高频查询（TTL + 主动失效）。

## 附：面试可用的说法（万一被追问）

| 可能被问 | 怎么答（口语版） |
|---|---|
| 这个 AI 助手和普通聊天机器人有什么区别？ | 它不只是聊天，它**能去查我们系统的真实数据、也能改数据**。所以我把重点放在两件事上：一是给它按角色划清能做什么（学生查不到别人的、教师碰不到绩点），二是凡是要改数据的操作，先弹卡片让用户点确认，确认前数据库一点变化都没有。 |
| 你怎么知道它"回答得对"？ | 我写了个脚本，把 10 个典型问题（学分够不够、绩点多少、下周有考试吗…）真的发给大模型跑一遍，再核对两件事：它有没有挑对功能、它给出的数字跟数据库里的是不是一致。现在 10/10。 |
| 遇到过什么问题？ | 印象最深的两类：一是模型会**编参数**——学生问"数据结构与算法和我课表冲突吗"，它猜了个课程编号，查出来是"课程不存在"；后来我把接口改成能直接按课程名/课程代码查。二是**同一个账号在别处重新登录，会把它正在输出的回答掐断**，这是个真 bug，修完之后补了测试。 |
| 为什么用 SSE / 为什么自己写循环？ | 回答要边生成边显示（打字机效果），所以用流式推送。循环是"模型要调工具 → 执行 → 把结果回给模型 → 继续回答"这个过程，我自己实现是为了把权限校验、确认卡片、审计、限流都插在这个过程的关键位置上。（注：下一步计划换成成熟的 Agent 框架，把这套手写逻辑迁移过去，并补上多轮对话记忆。） |
| 现在还有哪些不足？ | 最明显的是**还没有多轮记忆**——现在是一问一答，用户没法追问"那第二门呢"，这是我下一步要做的；另外知识库（比如重修政策）还没接，政策类问题目前靠模型常识，需要补文档检索。 |

> ⚠️ 提醒：`drop_course`（退课）目前**不弹确认卡片**（选课/录成绩/开课申请/审批都弹）。
> 简历里写的是"涉及重要变更的操作会先确认"，与实现一致；若被追问退课，可答
> "退课风险低于选课（不占名额、可重新选），所以我没要求确认；如果要做成一致也很好改"。

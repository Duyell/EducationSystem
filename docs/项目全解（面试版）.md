## §0 三套自述模板（背下来）

**30 秒版（自我介绍里的一行）**
"我独立做了一个教务系统，在上面实现了一套 LLM Agent：把 33 个教务业务能力封装成工具，
用大模型的工具调用（Function Calling）驱动一个自研循环，让助手能查真实数据、能办业务；
因为模型不可信，我在执行前后加了四道闸门——角色白名单、参数校验、危险操作人工确认、全量审计，
确认之前数据库不会有任何变化。"

**2 分钟版（被问"讲讲你这个项目"）**
1. **业务底座**：教务系统本体——培养计划与毕业学分审核、绩点与专业内排名、排课与教室推荐、
   选课轮次与选/退课、考试安排；25 张表、多模块分层。
2. **为什么做 Agent**：这些业务都要求"查数据 + 算规则 + 改数据"，很适合自然语言入口；
   但教务数据的变更（选课占名额、改成绩）不可逆，所以**可控性比智能程度更重要**。
3. **怎么做的**：工具用 Spring AI 的 `@Tool` 声明、参数 Schema 由框架生成；
   我自研编排循环负责"模型请求工具 → 校验 → 执行 → 回填结果 → 再问模型"，
   直到模型不再请求工具；流式输出用 SSE。
4. **安全**：四道闸门 + 输出护栏 + 限流 + 幂等键。
5. **知识问答**：制度文档走 RAG（pgvector + bge-m3），并做了服务端强制检索。
6. **怎么证明它好**：自建评测——CI 里用确定性假模型跑 11 套链路断言，
   真实模型侧用黄金集验工具选路与制度问答忠实度。

**5 分钟版**：在上面的骨架上，每条补一个**具体决定 + 为什么**（见 §3–§8），
最后补 §13 的 1~2 个坑（最能体现深度）。

## §2 核心链路（最重要的一章，务必能画出来）

### 2.1 全链路总图

```
浏览器（Vue）
  │  fetch + ReadableStream 手写 SSE 解析（不用 EventSource，因为要带 token 头）
  ▼
LoginInterceptor（JWT + Redis 比对 + 按路径的角色规则）
  ▼
AiController.chat()  → AiChatService.chat()
  ├─ AgentRateLimiter.allowChat()           // 每人每分钟最多 10 次
  ├─ 先返回 SseEmitter（HTTP 立即响应，不等模型）
  └─ CompletableFuture.runAsync(...)        // 后台线程跑，不占 MVC 线程
        └─ processChat()
            ├─ 选 system prompt（按角色三套常量）
            ├─ resolveConversation()        // 归属校验 + 角色一致性；失败直接错误收尾
            ├─ historyMessages()            // 取最近 20 条（先读历史，再写本轮）
            ▼
        AgentRuntime.run(Request, events)
            ├─ ContextAugmenter 链（制度意图 → 强制检索注入）
            └─ for (iteration < 5)                       ← ★ 循环
                ├─ OpenAiClient.streamChat(messages, tools)  ← 带 33 个工具的清单
                │    ├─ 逐 token：ToolCallTextGuard.feed() → events.publish(TOKEN)
                │    └─ 解析出本轮的 tool_calls
                ├─ 无 tool_calls → publish(DONE)，返回 Outcome(completed)
                └─ 有 tool_calls → 逐条处理：
                    1) 工具名不在注册表 → audit(DENIED) + 回灌"已拦截"
                    2) 参数 Schema 校验失败 → audit(INVALID_ARGUMENTS) + 回灌原因
                    3) risk == DANGEROUS → awaitConfirmation()  ← 挂起（§2.3）
                    4) 否则 → ToolRegistry.executeForRole() → audit(SUCCESS/FAILED)
                       → 结果作为 role=tool 消息追加 → 下一轮
            ▼
        落库助手正文 + 出处（sources_json）→ emitter.complete()
  ▼
前端按事件渲染：打字机正文 / 工具执行状态 / 确认卡片 / 来源卡片
```

### 2.2 主链 A：只读问答（"我绩点多少"）

逐方法追踪（**照着代码走一遍，面试就能讲**）：

| 步骤 | 类.方法 | 干什么 |
|---|---|---|
| 1 | `AiController.chat()` | 取 token、调用服务、返回 `SseEmitter` |
| 2 | `AiChatService.chat()` | 限流（`AgentRateLimiter`）→ 建 emitter → `CompletableFuture.runAsync` |
| 3 | `AiChatService.processChat()` | 三层事件装饰：`SourceCapturingPublisher(SseAgentEventPublisher(emitter))` |
| 4 | 同上 | 按角色选 `SYSTEM_PROMPT_*`（Java 常量，三套） |
| 5 | `resolveConversation()` | 归属校验（不是自己的会话直接拒）+ 角色一致性 + 首条消息生成标题 |
| 6 | `historyMessages()` | **先读历史、再写本轮用户消息**（顺序反了模型会看到两遍同一句） |
| 7 | `AgentRuntime.run()` | 循环主体 |
| 8 | `withAugmentedContext()` | 制度类问题：先检索并注入真实条款（§7.6） |
| 9 | `OpenAiClient.streamChat()` | 组装请求（messages + tools + stream）→ 发 HTTP → 解析 SSE |
| 10 | `ToolCallTextGuard.feed()` | 逐 token 过护栏（§3.5），干净 token 才推给前端 |
| 11 | `ToolRegistry.getTool(role,name)` | 白名单查表（按「角色+名字」） |
| 12 | `JsonSchemaToolArgumentValidator.validate()` | 参数二次校验 |
| 13 | `ToolRegistry.executeForRole()` | `ChangeContext.runWith(userId, role, SOURCE_AI, …)` 里执行，业务层据此区分来源 |
| 14 | `AiAuditService.record()` | 落审计 |
| 15 | `publishSourcesIfAny()` | 工具结果形如 `{"results":[{"citation":…}]}` 就转发来源事件 |
| 16 | `AiChatService` 收尾 | `appendAssistantMessage(正文, lastSources)` 落库 → `emitter.complete()` |

**8 种事件**（`AgentEventType`）：`TOKEN`（正文增量）、`STATUS`（"正在执行…"进度）、`CONVERSATION`（会话 id）、`CONFIRM`（确认卡片）、`CONFIRM_RESULT`（确认结果）、`ERROR`、`SOURCES`（来源）、`DONE`。

### 2.3 主链 B：危险写操作（"帮我选课"）

只读链走到第 3 道闸门时开始分叉：

```
模型请求 select_course(courseId=7)
  ├─ risk == DANGEROUS
  ├─ ConfirmationGate.suspend(confirmId, action, timeout)
  │    ├─ PendingActionStore.save(action, TTL=180s)     // Redis：工具名 + 参数
  │    └─ 线程在 CompletableFuture 上等待（最多 180 秒）
  ├─ events.publish(CONFIRM, confirmId, 展示名, 参数摘要)   // 前端弹卡片
  └─ 本轮结束 —— **数据库零变化**

用户点「确认」→ POST /ai/confirm {confirmId, approved:true}
  └─ AiChatService.resolveConfirmation() → ConfirmationGate.confirm() → 唤醒线程
      └─ AgentRuntime 恢复：
          ├─ 用 confirmId 作幂等键查审计（findExecuted）
          │    ├─ 已成功执行过 → 复用结果，audit(DUPLICATE_SKIPPED)
          │    └─ 否则 → executeForRole() → audit(SUCCESS)
          ├─ 结果作为 tool 消息回灌 → 继续循环 → 模型给最终回答
          └─ 用户取消/超时 → audit(REJECTED_BY_USER) + 一条"未对数据做任何修改"的收尾
```

**四个必须能答的细节**：
1. **前端只回传 `confirmId`，绝不回传工具名与参数**——否则等于把"任意工具调用权"交给前端；
   参数在服务端 Redis 里，用户改不了。
2. **连接断了不用等满 180 秒**：`onTimeout/onError/onCompletion` 里拿到当前挂起的 confirmId，
   立刻唤醒并释放。
3. **重复确认只执行一次**：`request_id` 唯一索引 + `findExecuted` 查询，第二次命中 `DUPLICATE_SKIPPED`。
4. **确认超时是"取消"而不是"拒绝"**：状态记 `REJECTED_BY_USER`，语义上等同于用户放弃。

### 2.4 三条结束路径，一处落库

`AgentRuntime.run` 的返回是 `Outcome(answerText, stopReason)`，
`stopReason ∈ {completed, cancelled, max-iterations}`；
三条路径的**落库都在 `AiChatService.processChat` 一处**完成。
> 这是重构顺手修掉的隐患：改造前三条路径各自落库一次，漏一处就少记一轮对话。
> 面试点：**"同一件事只允许一处实现"**——这个项目里反复出现（补考规则、冲突判据、检索实现）。

### 2.5 断线、超时、取消

| 情况 | 行为 |
|---|---|
| 用户关页面/断网 | `emitter.onError/onCompletion` → 唤醒挂起线程 → 释放，不等满超时 |
| 前端主动取消危险操作 | `POST /ai/confirm` 带 `approved:false` → 唤醒 + `REJECTED_BY_USER` |
| SSE 本身超时 | 主路径 `SseEmitter(5 * 60 * 1000L)`；错误/限流路径用 `new SseEmitter(0L)`（不设超时，只为把错误写回去） |
| 模型空响应 | `AgentRuntime` 检测到"没有正文也没有工具调用"→ 发一条 STATUS 并**重试一次** |

## §3 Agent 运行时的关键实现（`AgentRuntime.java`，467 行，精读）

### 3.1 循环骨架（伪代码）

```java
Outcome run(Request req, AgentEventPublisher events) {
    List<ChatMessage> messages = build(req.systemPrompt(), req.history(), req.userMessage());
    int maxIterations = max(1, aiProperties.getLimits().getMaxIterations());   // 默认 5
    for (int iteration = 0; iteration < maxIterations; iteration++) {
        ToolCallTextGuard guard = new ToolCallTextGuard(objectMapper);         // 每轮新护栏
        stream = openAiClient.streamChat(messages, toolsPayload, token -> {    // 带 33 个工具
            events.publish(AgentEvent.token(guard.feed(token)));               // 逐 token 过护栏
        });
        // 情况 1：模型没请求工具 → 结束
        if (stream.toolCalls().isEmpty()) { events.publish(done()); return completed(text); }
        // 情况 2：护栏把"写在正文里的工具调用"恢复出来了 → 按正常流程处理
        // 情况 3：逐条处理工具调用（白名单 → 参数校验 → 确认/执行 → 审计 → 回灌）
    }
    return new Outcome(text, "max-iterations");
}
```

**退出条件**：模型返回**不含 tool_calls** 的那一轮，就是最终答案。
**防死循环**：轮数上限 5（`ai.limits.max-iterations`）+ 单轮工具调用总数上限 20（`ai.limits.max-tool-calls-per-chat`）。

### 3.2 消息数组怎么长（面试常被要求"画出来"）

```
[ system   ] 角色说明书（三套之一）
[ user     ] "我绩点多少"
[ assistant] tool_calls=[get_my_gpa]        ← 模型"点菜"
[ tool     ] tool_call_id=…, content="{…}"  ← 我们"端菜"（结果 JSON）
[ assistant] "你的平均学分绩点是 3.2…"      ← 模型看到结果后作答
```
要点：`tool_call_id` 必须与请求对齐；工具结果**只作为数据**，不当指令处理（防提示注入）。

### 3.3 上下文增强（`ContextAugmenter`）

抽象接口 + `ObjectProvider<ContextAugmenter>` 注入 → 目前唯一实现是
`PolicyContextAugmenter`（制度意图 → 强制检索 → 把真实条款拼进 system prompt）。
**为什么做成"链"**：以后要加"学生画像注入""课表注入"不用改 runtime。

### 3.4 来源转发（运行时不需要知道 RAG 存在）

`publishSourcesIfAny(toolResultJson)`：只要工具返回的 JSON 里含
`{"results":[{"citation":…}]}` 形状，就转发一条 `SOURCES` 事件。
> 好处：运行时**不认识 RAG**，任何按这个形状返回的工具都能让前端出卡片。

### 3.5 输出护栏（`ToolCallTextGuard`，294 行）

**它解决什么**：7B 模型偶尔把工具调用**当正文写出来**（`<tool_call>…</tool_call>`），
前端会看到一堆 JSON 垃圾；更糟的是这个标签是**逐字符流式到达**的，
必须能在流中间识别并拦截。

**怎么做**：状态机按字符喂入 → 识别 `<tool_call>` 开始/结束 →
中间的内容**不推给前端**（返回空串）→ 结束时返回"恢复出的调用列表"；
`AgentRuntime` 拿到恢复的调用后**按正常流程处理**（校验/确认/执行），
而不是丢给用户看。
测试抓过真 bug：**`</tool_call>` 逐字符泄漏**（整段喂入的用例测不出来）。

### 3.6 限流（两道）

`AgentRateLimiter`：`ai:rl:chat:<userId>` 固定窗口 `INCR` + TTL 1 分钟（默认 10 次/分钟）；
另一道是单次对话内的工具调用总次数。
> 面试点：**固定窗口在边界有最多 2 倍突刺**，对"防滥用"足够；要精确计费才换滑动窗口/令牌桶
> ——能主动说出这个取舍，比背"我用了令牌桶"更可信。

## §4 工具系统（Agent 好不好用，八成取决于这一层）

### 4.1 一个工具的构成

`ToolDefinition` = `name` + `displayName`（项目加的，给人看）+ `description`（**给模型看**）
+ `parameters`（JSON Schema）+ `riskLevel` + `executor`。

### 4.2 用了框架的什么、刻意不用什么（**最高频的面试题**）

| Spring AI 能力 | 用没用 | 为什么 |
|---|---|---|
| `@Tool` / `@ToolParam` 声明 | ✅ | 省掉手写 JSON |
| `MethodToolCallback` | ✅ | 把方法包成可调用工具 |
| `JsonSchemaGenerator` | ✅ | **Schema 只有一个来源**，与校验器同源 |
| `ToolContext` | ✅ | 把 userId/role 传给工具方法（**绝不放进参数 Schema**，否则模型能伪造身份） |
| `ChatClient` | 🟡 仅试点 | 主链路没走它 |
| **框架的 tool-calling 自动循环**（1.x 在 `ChatModel` 内部） | ❌ **刻意不用** | 要在执行前**挂起等人确认**、执行后**过滤输出**、全过程**写审计**——这三件事插不进去 |
| `MessageWindowChatMemory` | ❌ | 它的 `saveAll` 是"替换整个窗口"语义，落 MySQL 会丢历史或消息翻倍（§6.2） |
| pgvector 自动配置 | ❌ | 它会拿**主数据源（MySQL）**去建 `vector` 表，启动即炸（§7.4） |

> **加分说法**：Spring AI 2.0 文档里专门有一节 *User-Controlled Tool Execution*，
> 列的适用场景正是"**外部审批门**""**把中间进度推给 SSE**""预算控制"——
> 与我手写循环的理由一致。也就是说这个方向是框架后来补上的官方扩展点，
> 我在 1.0.9 上先手写实现了同一件事。

### 4.3 项目侧的三个自定义注解

| 注解 | 解决什么 | 踩过的坑 |
|---|---|---|
| `@ToolMeta(displayName, riskLevel)` | 框架没有"展示名"和"风险等级"；缺了就抛异常**启动失败**（宁可起不来，也不要一个没有风险等级的写工具被当只读执行） | — |
| `@ParamConstraint(enum/min/max)` | 框架的 `@ToolParam` 表达不了 `enum`/`minimum`/`maximum`（成绩 0~100、评分 1~5） | 属性名对不上时**启动失败**（否则约束被静默丢弃，症状是"模型偶尔传越界值"，比启动失败难查一个数量级） |
| `ToolContext` 参数 | 身份从 token 来，**不进 Schema** | `MethodToolCallback` 要求声明了 `ToolContext` 的方法必须走两参重载 |

### 4.4 角色隔离（有真实事故）

`ToolRegistry` 用 `Map<角色, Map<工具名, 定义>>`，**同一工具名在不同角色下是两份独立定义**。

> **真实事故**：早期用"一个全局 Map 按名字索引"，学生与教师都有 `get_my_courses`
> （学生=我选的课，教师=我教的课），两个注册器互相覆盖 →
> 白名单校验**通过**、却执行了**教师那份实现**，用学号当工号查 → 返回空列表；
> 模型还拿到教师版描述，从提示词层就开始误导。
> 症状是"学生问'我选了什么课'，助手答'你没有选任何课'"，
> 而**所有既有测试都是绿的**（测试只看"工具在不在、角色对不对"，没看返回的数据）。
> 修法：定义按「角色+名字」隔离；跨角色同名只记一条 INFO。

### 4.5 注册时机（第二次真实事故，就发生在最近）

`DeclarativeToolRegistrar` 用 `InitializingBean` 注册；**任何"在建 Bean 时就快照工具表"的消费者
必须显式依赖它**。MCP 装配（`McpServerConfig#mcpToolSpecifications`）就是这样一个消费者。

> **真实事故**：迁移期两套实现（手写 + 声明式）并存，实测启动日志是
> `MCP 工具面已装配: 开放 14 个` 出现在 `声明式工具注册完成: 共 17 个` **之前 1.6 秒**
> ——也就是说外部 MCP 的 14 个工具一直跑的是**手写实现**，内置助手跑的是**声明式**，
> 同一批名字两套代码，只因为"谁先注册"由 Bean 顺序碰巧决定。
> 删掉手写实现时若不管这件事，MCP 会**静默暴露 0 个工具**，而覆盖性测试照样全绿。
> 修法：注册改回 `InitializingBean` + MCP 显式依赖它；
> 新增 `McpToolFaceAssemblyTest` **断言依赖边本身**（实测：删掉依赖边时，
> "工具面非空"那条断言**仍然是绿的**——只断言结果抓不住它）。

### 4.6 工具清单（33 个）

| 角色 | 数量 | 工具 |
|---|---|---|
| 学生 | 17 | `get_my_scores`、`get_my_gpa`、`get_my_training_plan`、`audit_my_graduation`、`recommend_courses`、`get_course_list`、`get_selection_status`、`get_my_courses`、`select_course`★、`drop_course`☆、`list_my_class_times`、`check_time_conflict`、`get_my_exams`、`get_my_evaluations`、`check_evaluation`、`evaluate_teacher`★、`get_my_academic_warning` |
| 教师 | 7 | `get_my_courses`、`get_course_students`、`enter_score`★、`update_score`★、`submit_course_apply`★、`apply_class_time`★、`get_my_evaluations` |
| 管理员 | 9 | `list_users`、`list_students`、`list_teachers`、`list_courses`、`list_classes`、`list_colleges`、`list_majors`、`get_statistics`、`approve_course_apply`★ |
| 跨角色 | 1 | `search_policy`（RAG 开启时才有，三角色通用） |

★ = `DANGEROUS`（执行前必须人工确认，共 **7 个**）；☆ = `WRITE`（可逆小改动，**不弹确认**）。

> **面试点（诚实且加分）**：退课标的是 `WRITE` 不是 `DANGEROUS`，所以**不弹确认卡片**。
> 理由：退课风险低于选课（不占名额、可重新选）。被追问就直说这个取舍，并说"要做成一致也很好改"。

### 4.7 工具描述怎么写（直接决定模型选不选得对）

- 描述里写**"什么时候用、什么时候不用"**，并给出"因此你该怎么办"；
- 写给**模型**看，不是写给同事看：领域词要说清（"培养计划"要解释成"毕业需要修哪些课"）；
- **描述会反过来改变模型行为**：曾写"用户确认后才执行"，模型就改成用**文字反问**
  而不去调用工具 —— 白名单/确认是**服务端**的事，不该写进描述里教模型。

### 4.8 新增一个工具的步骤（面试可能让你现场说）

1. 在对应角色的 `*DeclarativeTools` 里加一个 `@Tool` 方法：名字、描述（何时用/不用）；
2. 参数用 `@ToolParam`（可选参数**必须**显式 `required = false`，否则默认必填）；
3. 加 `@ToolMeta(displayName, riskLevel)`：写操作绝不能标 `READ_ONLY`（注册期会 WARN，评测脚本会 FAIL）；
4. 取值约束用 `@ParamConstraint`（enum/min/max）；
5. 需要身份的，加 `ToolContext` 参数（不要放进 Schema）；
6. 跑 `eval-p5-tools.cjs --inventory-only`（39/39）确认工具面不变量没破。

## §5 四道闸门与治理（企业级 Agent 的及格线）

### 5.1 ~ 5.4 四道闸门

| # | 闸门 | 实现在哪 | 拦什么 | 失败后怎么办 |
|---|---|---|---|---|
| 1 | **角色白名单** | `ToolRegistry.executeForRole` + `isAllowedForRole` | 越权调用（模型编出来的工具名 / 别的角色的工具） | 不抛异常，返回 `denied`，把原因当**工具结果回灌**让模型自我纠正；同时 `audit(DENIED)` |
| 2 | **参数 Schema 校验** | `JsonSchemaToolArgumentValidator` | 参数缺失/越界/类型错（模型会编参数） | 同上，`audit(INVALID_ARGUMENTS)`，回灌"参数不完整: …" |
| 3 | **人工确认（HITL）** | `ConfirmationGate` + `PendingActionStore` | 不可逆的数据变更 | 挂起 + 确认卡片（§2.3） |
| 4 | **审计留痕** | `AiAuditService` + `ai_tool_audit` | 事后回溯：谁、何时、调了什么、参数、结果、成功/失败 | 每次调用一行（含被拒的） |

**审计状态取值**（`AuditStatus`）：`SUCCESS` / `FAILED` / `DENIED` / `REJECTED_BY_USER` /
`INVALID_ARGUMENTS` / `DUPLICATE_SKIPPED`，并有 `isKnown()` 写入前自检。
> **真实事故**：MCP 桥接里手写过 `"ROLE_FORBIDDEN"`，不在取值集合里 →
> 按状态聚合的统计会**静默失真**，最后是被评测脚本"每个状态都是已知取值"这条断言揪出来的。

### 5.5 输出护栏、限流、幂等（第 5~7 项防护）

| 防护 | 作用 |
|---|---|
| `ToolCallTextGuard` | 拦住"模型把工具调用写成正文"（§3.5） |
| `AgentRateLimiter` | 每人每分钟 10 次对话 + 单次会话工具调用上限（§3.6） |
| 幂等键 | 确认令牌 = `request_id`，审计表唯一索引兜底（§2.3） |

### 5.6 为什么不能只靠提示词

面试标准答法：**提示词是"建议"，代码是"约束"**。项目里有两个证据：
① 危险操作若只写"请不要随便选课"，模型仍会调工具 → 必须服务端挂起；
② 制度问答若只写"请先检索"，7B 照样不检索就编 → 必须服务端强制检索（§7.6）。

## §6 记忆与上下文工程

### 6.1 存储与窗口

- 会话/消息落 MySQL（重启不丢、可查、可审计）；
- 模型上下文 = **最近 20 条**（`ai.memory.max-messages`，一问一答算两条 ≈ 10 轮）；
- **窗口只影响"模型能看到多少"，不影响落库的完整记录**（界面历史查得到全部）。

### 6.2 为什么不用框架的 `MessageWindowChatMemory`

它的 `saveAll` 语义是"用当前窗口**替换**整个会话"：落地到 MySQL 时，
要么把历史删了（丢历史），要么每轮把窗口重新插一遍（消息翻倍）。
所以自己实现 `MybatisChatMemory`：**只追加、读的时候取最近 N 条**。

### 6.3 一个顺序陷阱（面试可以主动讲）

`processChat` 里是**先读历史、再写入本轮用户消息**。
反过来写：本轮消息先落库，随后读窗口又把它读出来，再作为"用户输入"追加一次 →
**模型会看到两遍同一句话**。

### 6.4 归属与角色校验

`resolveConversation`：会话不存在或不属于当前用户 → 拒绝；
**会话创建时的角色与当前角色不一致也拒绝**（管理员改过权限的情况）。
> 这里刻意**不降级为"无记忆对话"继续跑**——那等于用一个错误会话 id 悄悄读别人的上下文。

### 6.5 出处落库

助手消息与 `sources_json` 一起写 `ai_message`。
> 缺口是实机发现的：来源最初只走 SSE 事件，**刷新页面卡片就消失**；
> 现在 `SourceCapturingPublisher` 在出口抄一份，和正文一起落库。

## §7 RAG 全链

### 7.1 为什么需要它

制度类问题（"绩点怎么算""重修有什么规定"）模型不知道，硬问就编。

### 7.2 语料与切分

| 项 | 值 |
|---|---|
| 语料 | `docs/policies/` 下 **11 份**制度文档（自撰的演示文本，非某校真实规章——§14） |
| 分块 | **85 个** |
| 切分 | `PolicyChunker`：**按章节切**（§2.3 这种语义单元），不是按字数 |
| 分块 id | 确定性且可读：`05-成绩构成与绩点换算办法#2.3#01` |

### 7.3 索引（幂等是硬要求）

`PolicyIndexer`：读 classpath 语料 → 切分 → 调 bge-m3 生成 1024 维向量 → 写 pgvector；
**重建时先按 docId 删旧块**（否则每次重建插入一批新块，检索结果里全是重复条款——
"幽灵条款"事故）。

### 7.4 向量库接线（为什么手工装配）

`RagConfig`：独立 PostgreSQL 数据源 + `PgVectorStore` + `initializeSchema(true)`（自动建表/索引/HNSW 余弦）。
两个坑：
1. **必须排除 pgvector 自动配置**：它的 `@ConditionalOnProperty` 带 `matchIfMissing`——
   不写属性也生效，会拿**主数据源（MySQL）**去建 `vector` 表，MySQL 没有该类型，启动即炸；
2. **第二个数据源会顶掉主数据源**：`DataSourceAutoConfiguration` 带
   `@ConditionalOnMissingBean(DataSource)`，所以必须在 `RagConfig` 里把 MySQL 数据源
   显式补回来并标 `@Primary`。症状极吓人：**连登录都失败**（`relation "sys_user" does not exist`）。
> 另有一个开关 `ai.rag.enabled`，**默认关闭**：关闭时应用完全不碰 PostgreSQL，
> 启动路径与没加 RAG 时一致。

### 7.5 检索参数

`ai.rag.top-k = 5`、`ai.rag.similarity-threshold = 0.35`、
表 `edu_policy_vectors`、维度 1024、HNSW 余弦距离。
> 阈值调高的后果是漏召回、调低是召回无关条款——面试可以主动说这个取舍。

### 7.6 服务端强制检索（**本项目最有价值的设计之一**）

**现象**：制度类问题，7B 有时**根本不调用 `search_policy`**，直接凭记忆作答，
甚至**复述工具的空结果文案假装查过、再编造文件名**。
**关键判断**：这不是检索坏了（同一问题直接检索 top1 命中正确条款），是**模型指令遵循不可靠**。
**修法**：把可靠性**从提示词搬到代码**——判定制度意图 → 服务端先检索 → 把真实条款注入上下文。
模型选不选工具都会拿到真条款。
> 面试点：**"能用代码保证的事，不要交给提示词"**。

### 7.7 引用回填与来源卡片

`search_policy` 的结果里带 `citation`（`JW-编号 + 文档名 + 章节`）→
`PolicySearchService` 回填 → `AgentRuntime.publishSourcesIfAny` 转成 `SOURCES` 事件 →
前端来源卡片 → 同时落 `ai_message.sources_json`。

### 7.8 评测（怎么证明 RAG 有效）

| 指标 | 结果 | 说明 |
|---|---|---|
| Hit@5 | **12/12（100%）** | 检索是否命中正确条款 |
| MRR | **0.944** | 命中位置的倒数排名均值 |
| 关键词命中率 | **100%** | 回答问题里是否出现应有条款 |
| 端到端忠实度（严格模式） | **9/9** | `--strict-faithfulness` 才算门禁 |

**为什么默认不计入退出码**：7B 措辞不稳定，端到端严格指标容易"碰运气式全绿/全红"，
所以默认是**诊断性**的，里程碑验收才开严格模式。

### 7.9 RAG 上踩过的坑

1. **幽灵条款**：重建索引不删旧块 → 检索里全是重复条款；
2. **把 top1 钉死在某份文档上**：某问题 FAQ 文档其实更贴切，断言写死了 → 测试变脆
   （教训：**断言业务事实，别钉死实现细节**）；
3. **"多条不同条款都提到 60 分"被误判成重复入库**：判据要用"分块 id 不重复"，不是内容相同。

## §8 事件协议与前端

### 8.1 为什么把事件出口抽象出来

`AgentEventPublisher` 生产实现是 `SseAgentEventPublisher`，**测试用"记录事件"的实现**——
于是"不启动 HTTP 就能断言事件序列"成为可能（这是可测性，不只是解耦）。
能用枚举名小写做线协议，与历史前端逐字兼容。

### 8.2 SSE 传输细节

- 主路径 `SseEmitter(5 * 60 * 1000L)`；错误/限流路径 `new SseEmitter(0L)`；
- `onTimeout/onError/onCompletion` 三处都要**释放挂起中的确认**（§2.5）。

### 8.3 前端为什么手写 SSE

用 `fetch` + `response.body.getReader()` 手动解析，而**不是 `EventSource`**——
因为 `EventSource` 不能自定义请求头，而本项目所有接口都要 `token` 头。
> 面试点：这不是重复造轮子，是协议限制下的必要选择。

### 8.4 前端结构

| 文件 | 行数 | 职责 |
|---|---|---|
| `views/ai/index.vue` | 318 | 组合面：布局、会话切换、事件分发 |
| `views/ai/components/ChatMessageList.vue` | 540 | 消息渲染 + **来源卡片** + 工具执行状态 |
| `views/ai/components/ChatInput.vue` | 67 | 输入与发送 |
| `views/ai/components/ConversationSidebar.vue` | 168 | 会话列表/新建/删除、`?conversationId=` |
| `composables/useAgentChat.ts` | 250 | **SSE 解析 + 状态机**（`pendingSources` 处理时序） |

**时序坑（务必记住）**：来源事件在**工具执行完**就发，而助手消息要等模型**下一轮开始吐 token**
才创建 → **来源先于消息到达**。`useAgentChat` 用 `pendingSources` 暂存、建消息时挂上。

## §9 业务能力 P1–P5（被问"业务有什么难的"时用）

### 9.1 培养计划与毕业学分审核（`CreditServiceImpl`）

按"专业 + 年级"定位培养方案 → 必修**逐门判定**（输出 `missing` 列表与缺失状态）→
选修学分统计 → 总学分统计。
**设计要点**："是否通过"一律委托 `GpaService.isPassed`，**不在这里重复实现补考规则**
（"规则只有一处实现"）。

### 9.2 绩点与专业内排名（`GpaServiceImpl`）

| 规则 | 值 |
|---|---|
| 分数 → 绩点 | **分数 / 10 − 5**（60→1.0、75.76→2.576、87.365→3.7365、100→5.0） |
| 精度 | 绩点 3~4 位小数（用户例子含 3 位小数分数） |
| 补考通过 | **一律按 60 分**计入 |
| 不及格 | **不计入** GPA |
| 同课程代码多条成绩 | **取绩点最高的一条**（避免重修拉低 GPA；设计文档未规定，按对学生有利处理） |
| 排名 | 同**专业 + 年级**内排名，只返回本人名次，不含他人明细 |

### 9.3 排课与教室推荐（`ScheduleServiceImpl`）

- 冲突判据（课表）：**闭区间重叠**——`weekday` 相同 且
  节次区间相交（`start ≤ other.end AND end ≥ other.start`）、周次区间相交、同一学期；
- 教室推荐：`status=1` 且 `capacity ≥ 需求` 且**该时段无课**，按容量升序（够用就好）；
- 教室数据：**800 间**（库里实测）。

### 9.4 选课轮次与六道校验（`CourseSelectionServiceImpl`）

**"六道校验链"**（第 1、2 道在 `statusFor` 里，3~6 在 `selectionBlocker` 里）：

| # | 校验 | 失败话术 |
|---|---|---|
| 1 | 轮次开放 | "当前不在选课开放时间内" |
| 2 | 适用范围（专业/年级） | 轮次配置的原因 |
| 3 | 学分上限 | "超过本轮学分上限（上限 X，已选 Y，本课 Z）" |
| 4 | 未修过（同 `course_code` 且已通过） | "你已通过课程代码为 X 的课程，无需重复修读" |
| 5 | 无时间冲突 | "与已选课程时间冲突：《课名》(代码) 周三 3-4 节 第1-16周…" |
| 6 | 容量未满 | "该课程名额已满（上限 N 人）" |

**设计要点**：校验方法**返回"不能选的原因"而不是抛异常**，
因为"可选课程列表"要复用同一套判断（把原因显示在按钮旁，而不是整页报错）。
并发安全：事务内先对课程行加锁（`select ... for update`），否则容量校验会被并发绕过。

### 9.5 考试安排（`ExamServiceImpl`）

- 冲突判据：**半开区间**（连续时钟，`[start, end)`）——
  允许"上一场结束即下一场开始"；
- **与 P2 的节次闭区间判据是两套语义，注释里明确写了"不要互相统一"**；
- 冲突即拒绝（不允许冲突），改期也要重新检测。

### 9.6 成绩变更日志（`score_change_log`）

- **挂钩点在 `ScoreServiceImpl`**（全部成绩写入的必经之路），
  所以"界面改的"与"AI 改的"两条路径都覆盖；
- 记录 `before_*` / `after_*` 快照（平时/考试/补考/总评/是否通过）+ 操作人 + 来源；
- 来源靠 `ChangeContext`：工具执行时 `ToolRegistry.runAsAi` 用
  `ChangeContext.runWith(userId, role, SOURCE_AI, …)` 标记，界面路径默认 `UI`；
- 管理端只读页 `/score-change-log`（`仅管理员`，逐字段"改前 → 改后"差异渲染）。

### 9.7 学业预警（`academic_warning` + `AcademicWarningServiceImpl`）

- 口径：**未通过课程学分累计 ≥ 8**（可配 `ACADEMIC_WARNING_THRESHOLD`，恰好等于也算触发）；
- **水位线**：达到条件 且（从未确认过 **或** 情况比上次确认时更严重）才提示 → "只弹一次"；
- 确认（标记已读）**幂等**：唯一键 `(student_id, failed_credits)`，重复确认捕获 `DuplicateKeyException` 视为成功但未新增；
- 未达条件时**不写水位线**（否则会把"未预警"记成已确认）；
- 统计未通过课程：按 `course_code` 归并，**有一条通过就不算未通过**，学分取各条最大值。

## §10 评测与工程化（**这是最能体现"工程能力"的一章**）

### 10.1 为什么自建评测

"我跑了一下没问题"不是证据。要能回答"这版比上版好吗""这个改动有没有把链路弄坏"。

### 10.2 确定性假模型（`.dsh/fake-model.cjs`）

一个 **OpenAI 兼容的 SSE 桩**：只照抄收到的历史（不会真思考），

**失败必然意味着链路坏了，而不是"今天模型心情不同"**。

### 10.5 两条"工程纪律"（面试讲这个最加分）

1. **基础设施问题不许伪装成断言失败**：读不到数据库、mysql 客户端不存在、
   环境没配模型 → 一律 **SKIP 并打印原因**，不计 FAIL。
   （这条纪律是被真实事故逼出来的：Windows 硬编码的 mysql 路径在 CI 上不存在，
   被脚本当成"夹具残留"报了一堆假失败。）
2. **断言强度要实测**：写"工具面非空"这种断言很容易写成永远绿的；
   所以真正钉住问题的是**断言依赖边本身**（§4.5）——而且我实测过：
   删掉依赖边时，结果型断言仍然绿。

### 10.6 其他工程化细节

- CI 21 个步骤：导入建表种子 → 326 项后端测试 → `vue-tsc` → 前端单测 → 打包 →
  起假模型 → 起后端 → 11 套断言；**只跑不依赖真模型的部分**；
- 前端测试：**15 个单测**（Vitest，第一份是给"成绩变更日志差异推导"写的）
  + **8 套 Playwright 实机**（P1–P4 页面、会话侧栏、来源卡片、学业预警、成绩变更日志）；
- 推前门禁 `.dsh/pre-push-check.ps1`：后端测试 + 类型检查 + 前端单测（环境不足则 SKIP 并说明）；

## §11 MCP 对外能力（**简历没写，但技术上做了**——被问到能讲）

- **做什么**：把同一套工具面用 MCP 协议（官方 Java SDK 0.18.3 + SSE）开放给外部客户端
  （Cursor / Claude Desktop），让**别人的模型**也能用这些工具。
- **三个设计决定**：
  1. **暴露策略单点决定**：`McpToolExposure`——`READ_ONLY` 始终开放（学生面 14 个）、
     `WRITE` 需 `ai.mcp.allow-writes=true`、**`DANGEROUS` 永不外放**
     （它的安全性依赖人工确认，而 MCP 没有这条通道）；启动日志逐条打印"开放了什么、为什么排除别的"；
  2. **身份不来自客户端自述**：取自 `LoginInterceptor` 校验后写入请求的 `username/role`，
     并要求等于本实例配置的角色面；
  3. **不新增第二条执行路径**：外部调用与内置助手最终都走 `ToolRegistry.executeForRole`，
     所以白名单、审计、"界面改的还是 AI 改的"语义自动继承；
     审计用 `session_id = mcp:<会话号>` 与内部调用区分（运行时路径该列一直是 null）。
- **踩的坑**：删除手写注册器时发现 MCP 装配早于工具注册（§4.5）；
  以及"客户端把消息 POST 到 SSE 端点被报成 **500**"——MCP 客户端靠 **4xx** 触发"回退到 SSE"，
  回 5xx 等于告诉它"服务器坏了"，它连回退都不试（现象只有一句 `connect_failure`）。
  修法：`GlobalExceptionHandler` 把 `NoResourceFoundException` → **404**、
  `HttpRequestMethodNotSupportedException` → **405**。
- **验证**：`verify-mcp.cjs` 协议级 **PASS=30 FAIL=0**（含"回退契约"两条断言）；
  官方 Inspector CLI 列出 14 个工具、`tools/call get_my_courses` 返回真实课程数据；
  Cursor 实机连接成功（`Successfully connected to sse server`）。
- **还没做**：stdio 传输、按会话动态工具面（一台实例一个角色面）。

## §12 面试问答 60 问（按类别，答法都用本项目的事实）

### A. 概念与取舍（1–8）
1. **什么是 function calling？和 RAG 什么区别？** 工具调用是"做事"（模型输出结构化的调用请求，
   我们执行并把结果回填）；RAG 是"查资料"（先把相关文档段落找出来塞进上下文）。
   本项目两者都有：业务工具 + `search_policy`。
2. **Agent 和"聊天机器人 + 工具"的区别？** 自主决策链：模型能基于**工具结果**决定下一步，
   循环到不再需要工具为止。本项目还多一层：危险动作要过人工确认。
3. **消息角色有哪些？`tool_call_id` 干什么？** system/user/assistant/tool；
   `tool_call_id` 把"工具的返回"与"模型的请求"配对，一轮多工具并行时靠它对齐。
4. **怎么防死循环？** 轮数上限 5 + 单轮工具调用总数 20 + 退出条件是"模型不再请求工具"。
5. **框架给了什么、你必须自己写什么？** 框架给声明、Schema 生成、参数绑定；
   授权/确认/审计/上下文策略/输出过滤必须自己写（§4.2）。
6. **什么时候不该自己写循环？** 当你的需求落在框架循环能力内（不需要挂起等人、
   不需要自定输出过滤、不需要细粒度审计）——那时自研就是负债。
7. **为什么 1.x 的循环插不进 HITL？** 循环在 `ChatModel` 内部，执行前没有你的钩子；
   官方 2.0 才提供 User-Controlled Tool Execution 与 Advisor hook（§4.2）。
8. **你这套和 LangGraph 的状态机比呢？** 我用"循环 + 事件契约"，因为流程是线性的
   （问 → 工具 → 再问）；多分支、多角色协作才需要显式状态机。

### B. 工具设计（9–16）
9. **工具描述重要还是参数 Schema 重要？** 都重要但**描述更容易被忽视**：
   描述写"何时用/不用"直接决定选不选得对；描述没写好，Schema 再准也没用。
10. **参数里能不能放 userId？** 绝对不能——模型能伪造。身份走 `ToolContext`（不进 Schema）。
11. **可选参数怎么表达？** `@ToolParam(required = false)`——**默认是必填**，
    这是框架的坑：模型省略就被校验器拒掉。
12. **框架表达不了 `enum`/`min`/`max` 怎么办？** 加一层 `@ParamConstraint` 合并进 Schema，
    并且属性名对不上就**启动失败**（静默丢弃约束比启动失败难查一个数量级）。
13. **同名工具在不同角色下怎么办？** 必须是两份独立定义（按「角色+名字」存）——
    否则会执行错实现并返回错数据，而所有测试还是绿的（§4.4）。
14. **工具返回什么格式？** 结构化 JSON（便于模型理解、也便于前端渲染）；
    异常细节不回灌模型（避免泄漏 SQL/表结构），只在结果里给可读原因。
15. **工具报错怎么办？** 不抛异常给用户，而是把 error 作为 tool 结果回灌，让模型自我纠正并解释。
16. **怎么加一个工具？** §4.8 六步。

### C. 安全与治理（17–27）
17. **四道闸门是什么？** 角色白名单 → 参数 Schema 校验 → 危险操作人工确认 → 全量审计。
18. **为什么要 HITL？** 白名单与校验只能保证"格式对"，保证不了"该不该做"；
    选课占名额、改成绩不可逆。
19. **确认卡片怎么实现？** 服务端把"工具名+参数"存 Redis（TTL 180s），线程挂起等；
    前端只回 `confirmId`；确认到达唤醒线程，取参数执行。
20. **用户点确认前进程在干什么？** 那个请求的后台线程 park 在
    `ConfirmationGate` 的 `CompletableFuture.get(timeout)` 上。
21. **连接断了怎么办？** `emitter.onError/onCompletion` 拿到当前 confirmId 立刻释放，不等满超时。
22. **重复点确认会不会选两次课？** 不会：`confirmId` 同时是幂等键，
    审计表 `request_id` 唯一索引，第二次命中 `DUPLICATE_SKIPPED`。
23. **提示注入怎么防？** 输入与工具输出都不可信；工具结果只作为**数据**不当指令；
    权限最小化；身份不进参数。
24. **越权调用怎么处理？** 不抛异常，返回 denied + 原因回灌（让模型换方式）+ 记 `DENIED` 审计。
25. **限流怎么做的？** Redis 固定窗口 `INCR` + TTL（每人每分钟 10 次）+ 单次会话工具调用上限；
    我明确知道固定窗口在边界有 2 倍突刺，防滥用够用。
26. **审计表为什么要有 `session_id`？** 区分"内置助手调用"与"外部 MCP 调用"（`mcp:<id>`），
    不加列就把两类调用分开了。
27. **为什么审计状态要用枚举/常量集合？** 状态会被聚合统计，写错字符串不报错、只会让统计静默失真；
    所以我加了 `isKnown()` 写入前自检（真实事故：手写过 `ROLE_FORBIDDEN`）。

### D. 记忆与上下文（28–33）
28. **多轮记忆怎么存怎么取？** 只追加完整记录到 MySQL；模型上下文取最近 20 条。
29. **为什么不用框架的窗口记忆？** 它的 `saveAll` 是"替换整个窗口"语义，落库会丢历史或翻倍。
30. **窗口该按条数还是轮数？** 按条数（一问一答两条），更直观也更好配。
31. **上下文太长怎么办？** 现在靠窗口 + 按需注入；摘要压缩**暂不做**（7B 下性价比低）。
32. **为什么"先读历史再写本轮"？** 顺序反了模型会看到两遍同一句话（§6.3）。
33. **会话切换怎么做？** `?conversationId=` 可分享可刷新；服务端做归属 + 角色一致性校验。

### E. RAG（34–42）
34. **文档怎么切？** 按章节（语义单元），不是按字数。
35. **为什么重建索引要幂等？** 语料还在改，反复重建不能产生重复/幽灵条款（先按 docId 删旧块）。
36. **向量库怎么选？** 规模小 → pgvector（复用 PostgreSQL、运维成本低）；大了再上 Milvus/Qdrant。
37. **相似度阈值怎么定？** 0.35；调高漏召回，调低召无关——要靠评测调。
38. **召回不准怎么排查？** 先看检索指标（Hit@5/MRR），再看模型：
    本项目发现"**检索 100% 命中但模型不调工具**"，所以问题在模型指令遵循，不在检索。
39. **怎么保证答案有据？** 引用回填 + 断言出处 + 服务端强制检索。
40. **强制检索怎么做的？** 识别制度意图 → 服务端先检索 → 注入真实条款，模型选不选都有真条款。
41. **出处为什么要落库？** 只推 SSE 事件的话，刷新页面卡片就没了。
42. **RAG 评测指标有哪些？** Hit@5、MRR、关键词命中率、端到端忠实度；前两个是检索层，最后一个是生成层。

### F. 评测与工程（43–52）
43. **怎么证明 Agent 比上版好？** 黄金集（选路）+ 分层指标 + **存档基线**。
44. **假模型是什么？为什么需要？** OpenAI 兼容 SSE 桩，只照抄历史 → CI 里断言变确定性：
    失败必然是链路坏了，而不是模型波动。
45. **评测怎么骗你？** 指标默认诊断性（措辞不稳）、只测路由不测业务数据、
    把 top1 钉死在某文档上、并发跑导致假性劣化（§7.9/§10.4）。
46. **为什么质量评测不进 CI？** 要真实模型 + 向量库，成本和稳定性都不合适；
    进 CI 的是链路级断言（假模型）。
47. **环境问题怎么处理？** 一律 SKIP + 打印原因，绝不计 FAIL（§10.5）。
48. **断言强度怎么保证？** 实测：写完之后把被保护的东西破坏掉，确认断言会红（§4.5）。
49. **CI 都跑什么？** 21 步 / 11 套断言（§10.3）。
50. **前端测了什么？** 15 个单测（纯函数：差异推导）+ 8 套 Playwright 实机。
51. **迁移框架怎么保证四道闸门不失效？** 闸门在 `ToolRegistry`/`AiChatService`，与工具写法无关；
    再加覆盖闸门测试（注册集合 == 声明式集合）与 Schema 形状断言。
52. **你怎么知道线上没坏？** 审计表 + 事件/状态日志；每个工具调用都有耗时与状态。

### G. 业务（53–57）
53. **绩点怎么算？** 分数/10−5；补考通过按 60；不及格不计；同课程代码取最高；专业内排名。
54. **选课的六道校验？** 轮次、范围、学分上限、未修过、时间冲突、容量（§9.4）。
55. **冲突判据为什么两套？** 课表按节次是**闭区间**，考试是**连续时钟的半开区间**
    （允许一场结束即下一场开始），语义不同**不要统一**。
56. **成绩变更日志有什么用？** 成绩可申诉 → 谁改的、改前改后、界面还是 AI 改的，全留痕。
57. **学业预警怎么避免骚扰？** 水位线：达到阈值且（没确认过或更严重）才提示；确认幂等。

### H. 反问与软性（58–60）
58. **这个项目最大的技术难点？** 不是调模型，而是**让不可信的模型在可审计的边界内干活**：
    工具按角色隔离、危险操作挂起、幂等、以及"用代码而不是提示词去保证可靠性"。
59. **如果重做会怎么改？** ① 把 Agent 能力抽成独立模块（现在是 `edu-api` 的子包）；
    ② 上 Spring AI 2.0 的 User-Controlled Tool Execution，把自研循环换成框架的扩展点；
    ③ 评测从"脚本集合"升级成平台（现在 30 个脚本已经有点重）。
60. **你觉得这套东西的适用边界？** 适合"业务规则明确 + 数据敏感"的场景；
    纯开放域问答、需要多 Agent 协作的复杂规划，这套（单 Agent + 强闸门）就不够了。

## §13 最值钱的 8 个坑（讲成故事，面试官最爱听）

| # | 坑 | 根因 | 修法与教训 |
|---|---|---|---|
| 1 | **同名工具跨角色互相覆盖** | 工具定义只按名字索引，注册顺序决定谁活下来 | 定义按「角色+名字」隔离；教训：**测试只看"工具在不在"是假安全，要看返回的数据** |
| 2 | **`</tool_call>` 逐字符流式泄漏** | 整段喂入的用例测不出流式边界 | 状态机按字符过 + 新断言"落库正文不得含工具调用残渣" |
| 3 | **单对象参数被框架再套一层** | `MethodToolCallback` 的 Schema 生成行为 | 传平铺参数；教训：**契约形状要断言，不能靠"编译通过"** |
| 4 | **`@ToolParam.required` 默认 true** | 不了解框架默认值 | 可选参数显式 `required=false` |
| 5 | **第二个数据源把主数据源顶掉** | `DataSourceAutoConfiguration` 的 `@ConditionalOnMissingBean` | 在 `RagConfig` 里显式补 `@Primary` MySQL 数据源；症状是"连登录都失败" |
| 6 | **工具描述反过来改变模型行为** | 描述里写了"确认后才执行" | 确认是服务端的事，**别写进给模型看的描述** |
| 7 | **"评测全绿但真机在错"** | 断言只覆盖路由与状态码，没覆盖业务数据 | 断言下沉到业务字段（如"返回的课程名对不对"） |
| 8 | **夹具随时间老化** | 相对时间在导入那刻被固化成绝对时间 | 提供 re-anchor 脚本；教训：**时间相关的夹具一定会腐** |

> 另外三个（最近才发生的，也很值钱）：
> **MCP 装配早于工具注册**（§4.5）、**客户端用错端点被报成 500 导致回退失效**（§11）、
> **审计状态游离在取值集合之外**（§5.4）。

## §14 诚实边界（能说清楚这些，比吹牛可信十倍）

| 项 | 事实 |
|---|---|
| **退课不弹确认** | `drop_course` 标的是 `WRITE` 不是 `DANGEROUS`；7 个 `DANGEROUS` 里不含它 |
| **制度语料是自撰的** | `docs/policies/` 11 份开头写明"演示系统配套制度文本……措辞自拟"，**不是某校真实规章** |
| **质量评测不进 CI** | 需要真实模型 + pgvector，是**有意为之**；进 CI 的是链路断言（假模型） |
| **7B 选路有波动** | 10/10 与 8/10 都出现过；模型评测必须独占跑（并发会让检索指标假性掉到 25%） |
| **`docker-compose.yml` 从未实跑** | 本机到 Docker Hub 不可达（`registry-1.docker.io` 超时、Docker 守护进程未启动）；实际路径是"本机原生三库 + 本地 Ollama" |

| **确认超时是 180 秒** | `ai.confirmation.timeout-seconds` 默认 180，不是 5 分钟 |
| **测试里的 6 项跳过** | 依赖外部服务（真实模型/pgvector 真机）的用例默认 SKIP |
| **多轮记忆没做摘要压缩** | 只做窗口；上下文真吃紧时再说 |

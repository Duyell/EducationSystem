## 一、背景与目标

### 1.1 为什么要做这次扩展

原系统是一个**记录型**教务系统：能增删改查学生、教师、课程、成绩，但**没有教学管理规则**。因此：

- Agent 只能回答"有哪些课""我的成绩是什么"这类**单表事实**
- 无法回答任何需要**规则判断**的问题（我该选什么课、学分够不够、时间冲不冲突、我排第几）

这次扩展的目标：**把系统从「记录型」升级为「有规则的教学管理系统」**，从而让 Agent 能回答判断类问题。

### 1.2 现状（实施前，务必核对）

| 项 | 现状 |
|---|---|
| 数据库表 | **11 张**：`college` `major` `clazz` `student` `teacher` `course` `course_selection` `score` `teacher_evaluation` `sys_user` `ai_tool_audit` |
| 数据链路 | `student.clazz_id` → `clazz.major_id` → `major.college_id`（可定位学生的专业与年级，`clazz.grade`） |
| 课程 | 12 条，**每行是一次开课**（含 `term` 学期、`credit` 学分、`class_hour` 课时、`max_student` 容量、`teacher_id`） |
| 成绩 | **全部及格**（每个学生「及格学分 = 总学分」），因此不及格链路无任何真实数据 |
| 已有 Agent 能力 | 21 个工具、危险操作 HITL 确认、审计、幂等、限流（阶段 0 已完成并验证） |

**关键事实：`course` 表没有「课程代码」概念**，同一门课不同学期开课是不同行。这是本次必须先解决的结构问题（见 §三.1）。

### 1.3 明确的非目标（本轮不做）

写清楚"不做什么"和"做什么"同样重要：

| 不做 | 原因 |
|---|---|
| 单双周排课 | 用户确认：不存在"半个月上一次"的课 |
| 排课**优化**（少空档、教室利用率、学生不撞车） | NP 难题，投入产出比低。见 §五.6 的 L0-L4 分层 |
| 绩点排名的缓存/物化表 | 数据量小（数十人/专业），实时计算足够；过早优化会锁死表结构 |
| 重修（同一门课再次修读）流程 | `score` 表现有唯一约束 `(course_id, student_id)` 不允许重复行。用户确认：用户只需补考，不涉及重修 |
| 学籍状态**相关逻辑** | 用户确认：本轮只加字段，逻辑后续补 |
| 补考以外的成绩异动（缓考、免修、学分认定） | 本轮范围外 |

## 二、核心业务规则（权威定义，实施时不得改动）

这一节是所有判断类功能的依据。**规则错了，上层全错。**

### 2.1 绩点与平均学分绩点（已与用户逐例确认）

**单科绩点**：

```
若 分数 < 60:        绩点 = 0
否则:                绩点 = 分数 / 10 - 5
```

**最简形式就是 `分数/10 - 5`**（及格线以上），例如 60→1.0、65→1.5、87.365→3.7365、100→5.0。

**用户原话的等价表述（更贴合"十位映射"的说法）**：

```
绩点 = floor(分数/10) - 5 + (分数去掉十位后的余数) / 10
```
例 87.365：floor(8.7365)=8（十位）→ 8−5=3；余数 = 87.365 − 80 = 7.365 → 7.365/10 = 0.7365；合计 **3.7365** ✓

**⚠️ 实现要点（此处已踩过一次错，务必照做）**
- ⚠️ **十位之后的余数必须整体除以 10**。设计初稿曾误写成
  `floor(分数/10) - 5 + 小数部分`（只加了小数，漏掉个位、也没除 10），
  用该式实算 75.76 得 2.76（应为 2.576）、87.365 得 3.365（应为 3.7365），
  **用户给的 13 条例子只通过 4 条**。修正后 11/11 全通过。
- 十位 = `分数 / 10` 向下取整 = `分数.intValue() / 10`（正数整除即 floor）。
  ❌ 不可用 `分数.intValue()` 当作十位（87.365 会得到 87）。
- **全程 BigDecimal，禁用 double**（double 会把 3.7365 算成 3.7365000000000002）。
- 建议直接实现 `score.divide(TEN).subtract(FIVE)`，更少出错；上面两种写法仅作对照。

**用户提供的全部验收例子（实现必须逐条通过）**：

| 分数 | 期望绩点 | 验证（分数/10 − 5） |
|---|---|---|
| 60 | 1.0 | 6 − 5 = 1 |
| 60.1 | 1.01 | 6.01 − 5 = 1.01 |
| 62.3 | 1.23 | 6.23 − 5 = 1.23 |
| 65 | 1.5 | 6.5 − 5 = 1.5 |
| 65.333 | 1.5333 | 6.5333 − 5 = 1.5333 |
| 75 | 2.5 | 7.5 − 5 = 2.5 |
| 75.76 | 2.576 | 7.576 − 5 = 2.576 |
| 85 | 3.5 | 8.5 − 5 = 3.5 |
| 87.365 | 3.7365 | 8.7365 − 5 = 3.7365 |
| 95 | 4.5 | 9.5 − 5 = 4.5 |
| 100 | 5.0 | 10 − 5 = 5 |
| 59.9 | 0 | 低于 60 |
| 0 | 0 | 低于 60 |

> 上表 11 条已用脚本实算验证过（含 60→1.0 这个特例），全部吻合。
> 注意 60 分：`60/10 − 5 = 1.0`，恰好等于用户要求的 1.0，**不存在特例分支**。

**【假设】精度**：`score` 三列均为 `decimal(5,1)`，即最多 1 位小数，因此"小数部分"实际最多 `.1`~`.9`。
但用户给出的例子含 `.76`、`.365`、`.333` 等 2~3 位小数，说明**用户预期支持更高精度**。
→ **建议实施时把 `score` 的 `usual_score`/`exam_score`/`total_score` 精度扩到 `decimal(6,3)`**，否则 75.76 无法录入。
此改动需同步前端表单与后端计算（`totalScore` 目前按 0.4/0.6 加权并 `setScale(1)`）。

**平均学分绩点（GPA）**：

```
GPA = Σ(单科绩点 × 该科学分) / Σ(该科学分)        ← 只统计「已通过」的课程
```

- **不及格课程不计入**（用户确认：不及格不算修完，学分不计入已修）
- 用户确认：**排名不需要额外处理**（同专业学生修的课相近，不存在"学分很少但绩点很高"的干扰）

### 2.2 及格、补考与已修学分

用户原话整理：

| 规则 | 说明 |
|---|---|
| 及格线 | 60 分 |
| 不及格 | **不算该课学分**、不视作已修完 |
| 补考 | 不及格者需补考；**补考通过一律记 60 分**；补考没过才算真没修完 |
| 已修学分 | 只累计「已通过」的课程学分（原始通过 或 补考通过） |

**判定优先级**：
```
通过 = (原成绩 >= 60) 或 (补考成绩 >= 60)
计入已修学分 = 通过
计入 GPA = 通过（补考通过的按 60 分算，即绩点 1.0）
```

### 2.3 必修 / 选修

| 类型 | 定义 | 毕业判定 |
|---|---|---|
| 必修 | 培养计划中明确列出的课程 | 必须**全部通过**（逐门判定） |
| 选修 | 培养计划中列为选修的课程 | 只要求**学分总和达标**，修哪些不限 |

**【假设】** 培养计划同时给出「总学分要求」与「必修学分要求」两个数值，便于分别校验。

### 2.4 时间冲突

用户确认：**不允许冲突**。判定条件（三者的交集）：

```
冲突 ⟺ 同一学期 且 星期几相同 且 节次区间有重叠 且 周次区间有重叠
```

- 节次：一天 10 节；上午 1、2 为一节课次（2课时），3、4、5 为一节课次（3课时），**也可只上 3、4**（2课时）
  → 因此用 `start_period`/`end_period` 表示区间，而不是固定两节或三节
- 周次：**必须支持非整学期**（用户明确：存在第 9 周开始、第 16 周结束的课）
- 不做单双周

## 三、数据库设计

### 3.1 需要先解决的结构问题：课程代码

**问题**：`course` 表每行是「一次开课」，同一门课不同学期是不同行。于是：
- 培养计划写"《Java程序设计》是第一学期必修"，指向哪一行？
- 判断"学生是否已修过这门课"，不同 `course_id` 如何认作同一门？
- 必修课补考，如何找到对应的课程定义？

**方案**：给 `course` 增加 `course_code`（课程代码，如 `CS101`）。**同一门课的所有开课行共用同一代码。**

**作用**：培养计划、已修判定、补考关联统一通过 `course_code` 关联。这是本次所有判断类功能的地基。

**【假设】** 代码由管理员在开课时填写（如沿用教务处的课程编号）。需提供数据回填脚本给现有 12 条课程。

## 四、业务逻辑层设计

### 4.1 分层与约定（照现有项目规范）

```
duyell/controller/   ← REST 接口（管理员/教师/学生页面用）
duyell/service/      ← 接口
duyell/service/impl/ ← 实现（业务规则集中在此）
duyell/mapper/       ← MyBatis Mapper（注解 SQL 或 XML）
com/duyell/*.java    ← 实体（edu-pojo 模块）
```

**强制约定**：
- 所有规则计算（绩点、已修学分、冲突检测、毕业判定）**只能写在 Service 层**，
  禁止写在 Controller 或 Mapper 里。理由：这些规则会被 REST 接口与 Agent 工具**同时复用**。
- Agent 工具的具体实现也调用同一 Service，**不得复制一份逻辑**。

### 4.3 关键算法

**（1）绩点换算**（`GpaService.gradePoint`）
```
输入 score (BigDecimal)
if score < passScore(60) → 0
绩点 = score / 10 - 5
```
例：60→1.0、75.76→2.576、87.365→3.7365、100→5.0。

> ⚠️ **本式曾被写错两次**（先按分段映射、再按「整数部分/10-5 + 小数部分」）。
> **正确式就是 `score/10 - 5`，60 分不特殊**——写作 `score/10 - 5` 时 60 自然得 1.0。
> 以 §2.1 为准，**不要**再引入"整数部分"或"小数拼接"的写法；改动前先跑
> `GpaServiceTest`（§2.1 的每条例子都有对应用例）。
>
> ⚠️ **必须用 BigDecimal 精确计算**，禁用 double（87.365 这类 3 位小数会丢精度）。

**（2）已修学分**（`CreditService.earnedCredits`）
```
取该学生所有 score 记录（按 course_code 去重，同一 code 取最高分/最优结果）
筛选 passed = true 的记录
按 course_code 关联课程学分，求和
注意：学分取自 course.credit（实际修读的课），而非 plan_course.credit
```

**（3）毕业审核**（`CreditService.auditGraduation`）
```
1. 定位学生适用培养计划（by major_id + clazz.grade）
2. 必修：逐门比对 plan_course(category=REQUIRED) 是否全部 passed
   → 输出「未通过的必修课清单」
3. 选修：统计已通过的选修课学分总和 ≥ elective_credits
4. 总学分：已修总学分 ≥ total_credits
5. 输出：{ 是否满足, 已修学分, 缺口, 缺失必修课[], 各分类明细 }
```

**（4）时间冲突检测**（`ScheduleService.checkConflict`）
```sql
-- 与「该教师的其他课」或「该教室的其他课」或「该学生的已选课」冲突
WHERE term = ?                -- 同一学期
  AND weekday = ?             -- 同一天
  AND start_period <= newEnd AND end_period >= newStart   -- 节次区间重叠
  AND start_week   <= newEndWeek AND end_week >= newStartWeek  -- 周次区间重叠
```
两个区间重叠的标准判据：`a.start <= b.end AND a.end >= b.start`。
**注意闭合区间**：第 3-4 节与第 4-5 节**算冲突**（第 4 节重叠）。

**（5）教室推荐**（`ScheduleService.recommendRoom`）
```
给定：学期、时间区间、容量要求
1. 取 status=1 且 capacity >= 需求的教室
2. 排除该时段已被占用的教室（重叠判据与 §4.3.4 逐字一致）
3. 按「容量、楼栋、楼层、房间号」升序，取前 N 个
4. 若无空闲 → 返回空并说明（区分"没有这么大的教室"与"该时段都占满了"）
```
**实现要点**：第 1~2 步用一条 `not exists` 反连接完成（等价于"查占用再做差集"，
但只需一次往返，且天然得到"容量最接近优先"的排序）。

**排序刻意不用自增 id**：800 间教室是批量生成的，插入顺序不保证，
新装库与现有库的 id 会不同，按 id 排会让推荐结果随安装而变、测试无法稳定断言。
按「容量 + 楼栋 + 楼层 + 房间号」排在任何库上都是同一个结果
（因此断言可以写"教1-101 被占时首推教1-102"）。

| `CreditServiceTest` | 已修学分：及格/不及格/补考通过（记 60）三种情形 |
| `ScheduleServiceTest` | 冲突判据：相接不算冲突（3-4 vs 5-6）、重叠算冲突（3-4 vs 4-5）、周次不重叠不算冲突（1-8 vs 9-16）、星期不同不算冲突 |
| `CourseSelectionValidatorTest` | 六道校验链逐条 |

**⚠️ 精度陷阱（必须写测试）**：绩点计算禁用 double。测试里要包含 `87.365 → 3.7365` 这类用例，
用 double 会得到 `3.7365000000000002`。

## 七、已知风险与注意事项

| 风险 | 说明 | 应对 |
|---|---|---|
| **课程代码回填** | 现有 12 条课程需填 `course_code`，且同一门课多学期共用 code | 提供回填 SQL；**不加唯一约束**（见 §3.3 风险 1） |
| **`score` 精度变更** | `decimal(5,1)`→`(6,3)` 影响存量数据展示与前端表单 | 单独一个提交，只做精度变更，便于回滚 |
| **`score.passed` 一致性** | 派生字段，分散维护必然不一致 | 只允许 `ScoreService` 写；成绩页与 Agent 工具都走它 |
| **冲突检测漏判** | 区间重叠写成 `>` 会漏掉"恰好相接"或"含端点"的情况 | 统一用 `a.start <= b.end AND a.end >= b.start`，并有边界测试 |
| **绩点精度** | double 会丢精度 | 全程 BigDecimal，有 87.365 用例护航 |
| **权限漏登记** | 新接口默认"仅需登录" | 每加接口必查 `LoginInterceptor.RULES`，并实测 403 |
| **测试污染** | 真实库只追加不清理 | 测试用随机标识；连跑两次验证 |
| **规模** | 11 张新表 + 5 张改造，比阶段 0 大数倍 | 严格按 P1→P5，每阶段独立可交付、可演示 |

### 8.4 已踩过的坑（**不要重犯**）

1. **`.dsh/` 下的 `.ps1` 必须纯 ASCII** —— Windows PowerShell 5.1 按 ANSI 读取，中文会破坏语法。
   中文断言改用 UTF-8 字节解码 + Unicode 码点（如 `[char]0x5BC6`）。
2. **`Invoke-WebRequest` 无 charset 时按 Latin-1 解 body** → 匹配中文会得到乱码与假阴性。
   读 `RawContentStream` 自行 UTF-8 解码。
3. **`@SpringBootTest` 默认回滚事务** → 写真实库的测试必须加 `@Transactional(NOT_SUPPORTED)`。
4. **真实存储的测试必须连跑两次** —— 只跑一次绿过不算数（曾因固定 user_id 累积而失败）。
5. **测试失败先确认外部依赖在线** —— Redis 未启动曾被误判为限流逻辑 bug。
6. **应用层长度限制与数据库列宽必须同时对齐** —— 只改一边会导致"修了一半"，
   而只查列宽的测试会放过它（`status` 截断事故）。
7. **工具描述必须写明"参数省略时的行为"** —— 否则模型会反问或编造参数（已踩）。
8. **`docs/开发记录.md` 是追加式，历史永不覆盖** —— 曾误覆盖丢失 70 行。
   用定点编辑，改完核对章节完整性。
9. **重建 fat jar 前先停后端**；**Maven 离线模式没有 `maven-install-plugin`**。

### 0.3 五个"必答"问题（其它都可以含糊，这五个必须张口就来）

1. **Function Calling 是怎么跑起来的？** → 模型只输出"要调哪个函数 + 参数"的结构化数据，**执行的是我们的代码**；执行完把结果以 `role=tool` 回填，再问一次模型；循环到模型不再请求工具。
2. **怎么防止 AI 乱改数据？** → 四道闸门：角色白名单 → 参数 Schema 校验 → 危险操作挂起等用户确认（Redis 存参数 + 令牌）→ 全量审计；**确认前零变更**，令牌兼作幂等键。
3. **秒杀怎么防超卖？** → Redis 预热库存 + Lua 脚本原子判断并预扣（判断与扣减在同一个脚本里，不会被打断）；扣成功的请求进 MQ 异步落库削峰；少卖靠对账补偿。
4. **库存扣减为什么用条件更新而不是先查再改？** → 先查再改在并发下会超卖（两个线程都读到 10）；`UPDATE ... WHERE remaining >= ?` 把判断和更新放在**一条 SQL** 里，靠数据库行锁保证原子性，再判影响行数。
5. **订单超时自动取消怎么做的？** → RabbitMQ 死信队列：消息先进带 TTL 的队列（或延迟队列），过期后转投死信交换机，消费者收到就取消订单并回补库存。

## §1 生鲜配送系统（高并发 Java 后端）

### 1.1 核心链路（能画出这张图）

```
选购 → 下单(扣库存/生成订单) → 支付 → (自提/配送分支) → 分拣(散称录实重) → 配送 → 核销 → 评价
        │                      │                                    │
        └ 超时未付 → DLX 延迟消息 → 取消订单 + 回补库存            └ 出库 FIFO（按过期日）
```

### 1.2 四个技术点的"为什么"

| 技术点 | 解决的问题 | 为什么这么做（面试重点） |
|---|---|---|
| **12 状态状态机** | 订单分支多（退款闭环、自提/配送），if-else 会失控 | 把"当前状态 + 事件 → 新状态"收敛成**一张表**（状态、允许的下一状态、触发事件），任何流转先查表；非法流转直接拒。好处是**加状态不用改业务代码**，且每一步可审计 |
| **条件更新扣库存** | 并发超卖 | `UPDATE batch SET remaining = remaining - ? WHERE id = ? AND remaining >= ?`——判断与扣减在同一条 SQL，靠 InnoDB 行锁串行化；`affectedRows == 0` 就说明库存不足，抛异常让整个事务回滚 |
| **DLX + TTL 延迟取消** | 超时订单占库存 | 下单时往延迟队列发一条消息，TTL 到期后进死信交换机 → 消费者取消订单并回补。**好处**：不依赖定时任务扫表，削峰且无延迟；**坑**：TTL 是**队列级**的（同一队列不同 TTL 会被队头阻塞），所以要么每个延迟档位一个队列，要么用延迟插件/时间轮 |
| **Redisson 分布式锁** | 多实例定时任务重复执行 | `@Scheduled` 在多实例下每个实例都会跑；用 `RLock`（可重入 + **看门狗自动续期**）保证同一时刻只有一个实例执行；**坑**：锁要设过期时间防死锁，但业务没跑完锁就过期 → 所以用看门狗续期；释放锁要判"是不是自己的锁"（Redisson 已用 Lua 保证） |

### 1.3 关键代码（白板能写出来就够）

**① 原子扣减库存（防超卖）**
```sql
-- 核心：判断与扣减在同一条 SQL，靠 InnoDB 行锁保证原子性
UPDATE batch
   SET remaining = remaining - #{qty}
 WHERE id = #{batchId}
   AND remaining >= #{qty}
   AND status = 1;
-- affectedRows == 0 → 库存不足，抛业务异常回滚整个下单事务
```

**② 下单伪代码（事务 + 幂等）**
```java
@Transactional(rollbackFor = Exception.class)
public OrderVO createOrder(CreateOrderDTO dto) {
    // 1) 幂等：同一请求号只下一单（唯一索引兜底）
    if (orderMapper.existsByRequestNo(dto.getRequestNo())) {
        return orderMapper.selectByRequestNo(dto.getRequestNo());
    }
    // 2) 按过期日 FIFO 取批次，逐批条件更新扣减
    for (Batch b : batchMapper.selectFifoBySku(dto.getSkuId())) {
        int n = batchMapper.deductIfEnough(b.getId(), need);   // 上一条 SQL
        if (n > 0) { need -= ...; if (need == 0) break; }
    }
    if (need > 0) throw new BusinessException("库存不足");      // 抛异常 → 事务回滚
    // 3) 生成订单 + 明细
    // 4) 发送延迟消息（超时未支付 → 取消 + 回补）
    rabbitTemplate.convertAndSend("order.delay.exchange", "order.delay", msg);
    return ...;
}
```

**③ 库存回补（按 JSON 快照回补，防止回补错批次）**
```java
// 扣减时把"用了哪些批次、每个多少"序列化成 JSON 存在订单明细里
// 回补时按这份快照逐条加回，避免"猜"该回补到哪个批次
for (BatchUsage u : objectMapper.readValue(detail.getBatchJson(), new TypeReference<List<BatchUsage>>() {})) {
    batchMapper.addBack(u.getBatchId(), u.getQty());
}
```

**④ RabbitMQ 延迟（DLX + TTL）配置要点**
```java
// 延迟队列：不设消费者，只等 TTL 过期 → 转投死信交换机
@Bean Queue orderDelayQueue() {
    return QueueBuilder.durable("order.delay.queue")
            .ttl(30 * 60 * 1000)                       // 30 分钟未支付
            .deadLetterExchange("order.dlx.exchange")  // 过期后去死信交换机
            .deadLetterRoutingKey("order.cancel")
            .build();
}
@Bean Queue orderCancelQueue() { return QueueBuilder.durable("order.cancel.queue").build(); }
// 消费者监听 order.cancel.queue：取消订单 + 按快照回补库存
```

**⑤ 秒杀：Lua 原子预扣**
```lua
-- KEYS[1] = 库存 key（string，预热写入）；ARGV[1] = 用户 id；ARGV[2] = 扣减数量
-- 返回 1 成功 / 0 库存不足 / -1 重复下单
if redis.call('SISMEMBER', KEYS[1] .. ':users', ARGV[1]) == 1 then return -1 end
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock < tonumber(ARGV[2]) then return 0 end
redis.call('DECRBY', KEYS[1], ARGV[2])
redis.call('SADD', KEYS[1] .. ':users', ARGV[1])
return 1
```
> **为什么用 Lua**：Redis 单线程执行脚本，**判断库存 + 扣减 + 记录用户**三步不会被打断；
> 如果分成三次命令，中间就会被并发插进来 → 超卖/重复下单。

**⑥ 限流注解（ZSet 滑动窗口 + Lua）**
```lua
-- KEYS[1] = 限流 key；ARGV[1] = 当前时间戳(ms)；ARGV[2] = 窗口(ms)；ARGV[3] = 上限
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])  -- 清掉窗口外的
local n = redis.call('ZCARD', KEYS[1])
if n >= tonumber(ARGV[3]) then return 0 end
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[1] .. '-' .. math.random())
redis.call('PEXPIRE', KEYS[1], ARGV[2])
return 1
```
> **为什么用 ZSet 而不是计数器**：计数器是固定窗口，窗口边界有 2 倍突刺；ZSet 记每次请求的时间戳，能实现真正的滑动窗口。
> **代价**：每个请求一条 ZSet 记录，内存与 O(logN) 成本更高——所以要 `ZREMRANGEBYSCORE` 清理并设过期。

**⑦ 缓存与安全**
```java
// Redis Hash 购物车：key = cart:{userId}, field = skuId, value = 数量+加购时间
redisTemplate.opsForHash().put("cart:" + userId, skuId, json);
// JWT 无状态认证 + 黑名单登出：登出把 jti/剩余有效期写入 Redis 黑名单，网关/过滤器先查黑名单
redisTemplate.opsForValue().set("jwt:blacklist:" + jti, "1", remainSeconds, TimeUnit.SECONDS);
```

### 1.4 高频追问（12 个，准备好答案）

1. **条件更新的影响行数是 0，事务会怎样？** → 抛业务异常 → 整个下单事务回滚（订单、明细都不落库）；不能只 return，否则会出现"订单已建、库存没扣"。
2. **为什么不用 `SELECT ... FOR UPDATE` 加锁？** → 可以，但会持有行锁更久、并发差；条件更新是"用一条 SQL 完成判断+更新"，锁窗口更短。也可以两者结合（先 `FOR UPDATE` 锁行再判断）。
3. **FIFO 按过期日先出，怎么做？** → 批次表带 `expire_date`，`ORDER BY expire_date ASC` 取可用批次，逐批扣；同一 SKU 多批次时循环扣。
4. **DLX+TTL 的延迟准吗？** → **不准**：TTL 是队列级，且消息在队尾，前一条没过期后面的就出不来（队头阻塞）。生产上要么每档 TTL 一个队列，要么用延迟插件（rabbitmq-delayed-message-exchange）或时间轮。
5. **消息重复消费怎么办？** → 消费端幂等：用订单号/消息 ID 做唯一键或状态判断（"已取消"就跳过）。
6. **消息丢了怎么办？** → 生产者确认（publisher confirm）+ 队列/消息持久化 + 消费者手动 ack；关键业务配本地消息表/定时对账。
7. **秒杀少卖了怎么办？** → Redis 预扣成功但 MQ 落库失败：靠**对账任务**（Redis 已扣名单 vs DB 订单）补偿；或者预扣时同时写一条流水，消费者落库后标记完成。
8. **Redis 挂了秒杀会怎样？** → 预扣层不可用 → 直接拒绝请求（**宁可拒绝也不能超卖**）；库存以 DB 为准，重启后重新预热。
9. **Redisson 锁的看门狗机制？** → 默认锁 30 秒，看门狗每 10 秒续期一次，直到释放；所以业务再慢也不会提前失效。若显式传 leaseTime，看门狗不生效，要自己保证业务时间 < leaseTime。
10. **限流用 ZSet 会不会有大 key 问题？** → 会：热点接口的 key 单值大。优化：按 用户+接口 拆分、控制窗口长度、用 `ZREMRANGEBYSCORE` + 过期、极端场景换令牌桶（固定内存）。
11. **12 状态状态机怎么落库？** → `order.status` 存当前状态；状态流转表（或枚举 + 允许流转集合）定义合法迁移；每次流转记录操作日志（谁、何时、从什么状态到什么状态）。
12. **退款闭环怎么保证钱和库存一致？** → 退款是**独立状态机分支**：申请 → 审核 → 退款中 → 已退款；库存回补与退款解耦（回补成功但退款失败要能重试），最终靠对账与人工兜底。

## §2 教务系统（Java 后端 + AI Agent）

### 2.1 核心链路（**这张图必须能画出来**）

```
POST /ai/chat（带 token）
 └─ 限流（每人每分钟 10 次）→ 建 SseEmitter（HTTP 立即返回，边算边推）
     └─ 后台线程跑 processChat：
         ├─ 按角色选 system prompt（学生/教师/管理员三套）
         ├─ 会话归属校验（不是自己的会话直接拒）→ 读最近 20 条历史 → 落库本轮用户消息
         └─ AgentRuntime.run(...)  ← ★ 核心循环
              ├─ 制度类问题：先强制检索制度条款并注入
              └─ for (轮次 < 5)：
                  ├─ 带上该角色的工具清单请求模型（SSE 流式）
                  │    └─ 逐 token 过输出护栏 → 推给前端
                  ├─ 模型没请求工具 → 结束，返回正文
                  └─ 模型请求了工具 → 逐条处理：
                      ① 工具名不在本角色注册表 → 拒绝 + 回灌原因 + 审计(DENIED)
                      ② 参数 Schema 校验不过 → 回灌原因 + 审计(INVALID_ARGUMENTS)
                      ③ DANGEROUS（选课/评教/录改成绩/申请开课排课/审批，共 7 个）
                         → 挂起：参数存 Redis（TTL 180s）+ 推确认卡片 → 本轮结束（数据库零变更）
                      ④ 否则执行 → 审计(SUCCESS/FAILED) → 结果作为 tool 消息回灌 → 下一轮
              └─ 结束：助手正文 + 出处一起落库 → emitter.complete()
```

### 2.2 四道闸门（简历上那句"角色白名单 → 参数校验 → 人工确认 → 审计留痕"的展开）

| 闸门 | 实现位置 | 拦什么 | 拦住之后 |
|---|---|---|---|
| ① 角色白名单 | `ToolRegistry.executeForRole` / `isAllowedForRole` | 越权：模型编出的工具名、别的角色的工具 | 不抛异常，返回 denied + 把原因**回灌给模型**让它自我纠正，同时审计记 `DENIED` |
| ② 参数 Schema 校验 | `JsonSchemaToolArgumentValidator` | 参数缺失/越界（成绩传 200 分这种） | 同上，审计记 `INVALID_ARGUMENTS` |
| ③ 人工确认 HITL | `ConfirmationGate` + `PendingActionStore` | 不可逆的写操作 | 挂起 + 确认卡片；**确认前数据库零变更** |
| ④ 审计留痕 | `AiAuditService` + 表 `ai_tool_audit` | 事后回溯 | 每次调用一行：谁/何时/工具/参数/结果/状态/耗时/会话号 |

> 另外还有三件防护：**输出护栏**（模型把工具调用写成正文时拦住）、**限流**（每人每分钟 10 次 + 单轮工具调用上限 20）、**幂等**（确认令牌 = 请求号，审计表唯一索引兜底）。

> **这几个词被追问时怎么说清（重要：别讲玄，它们都不高深）**：
> - **"参数 Schema 校验"就是普通的参数校验**（必填、类型、范围）。Agent 里唯一多出来的是：
>   **这套规则还要发给模型一份**让它知道怎么填 → 所以别手写那份说明，让它与校验规则**同源**
>   （本项目由框架从方法参数生成唯一一份，两处引用同一个对象）。不这样做就会出现
>   "检查比说明松 → 脏数据入库 / 比说明严 → 合法调用被拒"。
> - **"工具名不可信"** = 模型吐出来的只是一个字符串，它可能编一个不存在的名字、也可能请求别的角色的工具
>   （学生会话里请求 `list_students`）。所以**不能拿它直接执行**。
> - **"查表"查的是哪张表** = **不是数据库表**，是内存里的**工具注册表** `ToolRegistry`：
>   `Map<角色, Map<工具名, 工具定义>>`（学生 17 / 教师 7 / 管理员 9）。
>   代码就两句：`isAllowedForRole(role, name)` → `getTool(role, name)`。
>   **必须带角色**，因为同名工具在不同角色下是两份实现（`get_my_courses`：学生＝我选的课，教师＝我教的课）。

### 2.3 关键代码（**这些都可以直接讲，是真实实现**）

**① 声明式工具（一个工具就长这样，**下面这段是仓库里的真实代码**）**
```java
@Tool(name = "get_my_gpa",
      description = "查看**本人**的平均学分绩点、逐门课程绩点明细，以及本人在**同专业同年级**内的排名。"
                  + "学生问「我的绩点是多少」「我在专业里排第几」时使用。term 省略时返回全部学期累计；"
```

**② Agent 循环骨架（伪代码，面试口述版）**
```java
Outcome run(Request req, EventPublisher events) {
    List<ChatMessage> messages = build(req.systemPrompt(), req.history(), req.userMessage());
    int maxIter = 5, budget = 20, used = 0;
    for (int i = 0; i < maxIter; i++) {
        ChatResponse resp = client.streamChat(messages, toolsOf(req.role()), tok -> {
            String safe = guard.feed(tok);            // 逐 token 过护栏，防止工具调用泄漏成正文
            if (!safe.isEmpty()) events.token(safe);
        });
        if (resp.toolCalls().isEmpty()) return ok(text);        // ★ 退出条件
        for (ToolCall call : resp.toolCalls()) {
            if (++used > budget) break;
            ToolDefinition def = registry.getTool(req.role(), call.name());
            if (def == null) { messages.add(toolMsg(call, "无权限或工具不存在")); continue; }
            if (!validator.validate(def.parameters(), call.args()).ok()) {
                messages.add(toolMsg(call, "参数不合法")); continue;
            }
            if (def.riskLevel() == DANGEROUS && !gate.awaitConfirm(call)) {
                return cancelled();                             // 用户取消/超时 → 不执行
            }
            Result r = registry.executeForRole(def, req.role(), call.args(), req.userId());
            audit.record(req.userId(), req.role(), call.name(), call.args(), r, def.riskLevel());
            messages.add(toolMsg(call, r.payload()));           // ★ 结果回灌
        }
    }
    return maxIterationsReached();
}
```

### 2.4 高频追问（12 个）

1. **模型为什么能调用你的接口？** → 不是它调用，是**我们**调用。模型返回的是"工具名 + 参数"的结构化 JSON（`tool_calls`），我们查注册表、校验、执行，再把结果回填。
2. **为什么不用框架自带的循环？** → 框架的自动循环插不进三件事：危险操作要**挂起等人**、输出要**过滤**、全过程要**审计**。所以我只用框架的"工具声明 + 参数 Schema 生成"，循环自己写（Spring AI 2.0 后来专门提供了 User-Controlled Tool Execution 来支持这类需求）。
3. **确认卡片是怎么实现的？** → 参数存 Redis（带 TTL）、后端线程挂起等待、前端只回传 `confirmId`；**前端不回传工具名和参数**，否则等于把任意工具调用权交给前端。
4. **用户关掉页面会怎样？** → SSE 的 `onError/onCompletion` 回调里唤醒挂起的线程并释放，不用等满 180 秒。
5. **重复点确认会不会选两次课？** → 不会。`confirmId` 同时是幂等键，`ai_tool_audit.request_id` 上有唯一索引，第二次命中直接复用结果。
6. **模型编了个不存在的工具名？** → 白名单查不到 → 拒绝 + 把原因作为工具结果回灌，让模型自我纠正；同时审计记 `DENIED`。**不抛异常**（抛了用户就看到 500）。
7. **参数多了模型会传错怎么办？** → 执行前用**同一份 Schema** 再校验一次；越界/缺失就回灌原因让它重试。注意"给模型看的 Schema"和"我们校验的 Schema"必须同源（都由框架生成），否则会漂移。
8. **为什么每个角色只看到自己的工具？** → 一是减少模型选错（工具越多越容易选错，学生 17 个比 33 个准），二是**权限最小化**：教师面根本没有绩点工具，越权不可能发生。
9. **RAG 为什么按章节切？** → 固定长度会把一条规则从中间截断；按章节切保持语义完整，并且块里带文档名/章节号，回答才能标出处。
10. **模型不检索就编怎么办？** → 先把检索提到**服务端强制**：识别到制度类意图就自动检索并把真实条款注入上下文，模型选不选工具都能拿到真条款。（"能用代码保证的事不要交给提示词"）
11. **多轮对话的记忆怎么做的？** → 会话与消息落 MySQL（只追加、全量可查），喂模型时只取**最近 20 条**；没用框架自带的窗口记忆，因为它的 `saveAll` 是"替换整个窗口"的语义，落库会丢历史或消息翻倍。
12. **怎么证明这个 Agent 是"能用"而不是"能跑"？** → 两层：**链路层**在 CI 里用**确定性假模型**跑 11 套断言（工具面 39 项、隐私与审计 41 项、会话 31 项等），失败必然是链路坏了；**质量层**用真实模型跑黄金集（工具选路 10/10）和 RAG 评测（Hit@5 12/12、MRR 0.944）。

## §6 面试节奏建议

## §7 红线：不要主动说 / 被问到必须如实说

> 面试的底线是**不要说一件自己答不上来的事**。下面几条，主动说会加分（显得诚实），被问穿就很被动。

| 项 | 怎么说 |
|---|---|
| **简历上的教务系统描述比你仓库里最新版旧一点** | 面试前把简历与仓库对齐；如果被问到细节与你实际不同，**以实际实现为准**（"这部分我后来改过，现在是……"） |
| 制度文档是**自撰的演示语料**（不是某校真实规章） | 问就说"制度文本是我为演示系统自己写的，覆盖了学籍、考核、毕业审核这些主题" |
